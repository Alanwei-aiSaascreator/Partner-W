# 系统设计分析

## 五步设计框架
1. **需求收集**：列出功能需求（系统做什么）、非功能需求（规模、延迟、可用性、成本），以及团队规模、时间表和既有技术栈约束。区分已知事实和容量假设。
2. **总体设计**：画组件关系和数据流，标出API契约、存储选择与边界；优先识别既有可复用组件，不以新架构替换需求。
3. **深入关键路径**：设计数据模型、REST/GraphQL/gRPC等适用API端点；说明缓存策略、队列/事件、错误处理和重试逻辑，考虑重复执行、超时及一致性。
4. **容量与可靠性**：估算负载并展示计算假设；比较横向/纵向扩展，说明故障转移、冗余、监控与告警、单点及降级边界。
5. **权衡**：对复杂度、成本、团队熟悉度、上市时间与可维护性作明确比较；给出推荐和舍弃方案的原因。

## 输出结构
背景与范围 → 功能/非功能需求 → 显式假设和约束 → 组件/数据流图 → API与数据模型 → 容量及故障分析 → 方案比较 → 验证计划。
图可以用ASCII、Mermaid或清楚的文字描述；没有实测容量不能当性能承诺。指出系统增长到何种条件时需要重审设计。
所有实现、迁移、部署和监控配置动作只列为后续建议；技术选型依赖版本与服务能力时，先核实可靠来源或标待确认。

## 执行与交付边界
不改变现有权限、工具审批、工作区和文件产物合同。技能是工作流程，不是额外工具、连接或执行授权；只使用当前实际可用且在任务授权范围内的工具与资料。没有连接器时使用本地或用户提供的材料，不宣称平台已接通。
发布、部署、生产处置与对外通知仅输出建议清单或草稿；本技能不默许执行，也不自动创建工单、通知他人或后台监控。实际执行须由获授权的流程另行处理。
需要文件交付时沿现有能力生成并写入允许位置，校验 → 登记 artifact → 用户能打开 才算成功；未保存的文本称草稿，未跑的验证标 NOT RUN，不虚报完成。
