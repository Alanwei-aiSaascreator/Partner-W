# 架构决策记录

## 工作方式

先确认是在创建 ADR、评审已有设计，还是从需求设计新组件。读取用户提供的需求、现有架构与变更范围；把交付期限、团队经验、规模和预算列为约束。缺失的数据标为待确认，不把设想写成现状。

1. 梳理功能目标与非功能目标：延迟、可用性、成本、维护负担、团队能力。
2. 找到已有实现与历史 ADR；比较复用、局部调整和新组件，避免只围绕偏好的方案找理由。
3. 至少列出有实际意义的备选，按相同维度比较复杂度、成本、可扩展性和团队熟悉度。
4. 给出明确推荐及理由；说明放弃其他方案的代价、不可逆点、需要复核的假设。
5. 若需要系统设计细化，继续展开需求、组件、数据流、容量、故障与重试，无需假定另一个技能已安装。

## ADR 输出

- 编号、标题、日期、决策人；状态使用 Proposed / Accepted / Deprecated / Superseded，只有已有批准证据才写 Accepted。
- 背景：现状、约束、目标和决策驱动力。
- 决策：建议改变什么、保持什么、适用边界。
- 备选表：方案 / 复杂度 / 成本 / 可扩展性 / 团队熟悉度 / 优点 / 缺点。
- 权衡分析：为什么推荐方案更符合当前约束，哪些指标仍需实验。
- 后果：什么更容易、什么更困难、何时重新评估。
- 行动项：实施建议、负责人候选、验收点、后续复核时间；未获授权的变更不执行。

## 资料补充

可在已有授权范围读取历史设计文档、关联需求或工单；没有资料时列为待补，不声称查过。技术版本与产品能力需核实来源及日期，不凭旧资料作当前事实。

## 执行与交付边界

不改变现有权限、工具审批、工作区和文件产物合同。技能是工作流程，不是额外工具、连接或执行授权；只使用当前实际可用且在任务授权范围内的工具与资料。没有连接器时使用本地或用户提供的材料，不宣称平台已接通。
发布、部署、生产处置与对外通知仅输出建议清单或草稿；本技能不默许执行，也不自动创建工单、通知他人或后台监控。实际执行须由获授权的流程另行处理。
需要文件交付时沿现有能力生成并写入允许位置，校验 → 登记 artifact → 用户能打开 才算成功；未保存的文本称草稿，未跑的验证标 NOT RUN，不虚报完成。
