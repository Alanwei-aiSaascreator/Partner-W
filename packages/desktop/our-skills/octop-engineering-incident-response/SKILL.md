# 事故响应与复盘

## 确认阶段

明确是在初始分诊、过程更新，还是事后复盘；未明确时先确认。尽早记录已知事实，不等信息完美才记录；未知原因、影响和恢复时间明确待核。
本技能生成事故文档与建议，不授权操作生产、呼叫值班、建立群组、创建/更新远端事故或发送用户通知。

## 四阶段流程

1. **分诊**：评估严重度、受影响系统和用户；列出事故指挥、沟通和响应负责人候选及待确认职责。
2. **沟通**：准备内部状态更新和必要的客户通知草稿；建议沟通渠道、战情室和更新节奏，不自行创建或外发。
3. **缓解建议与记录**：提出方案、风险、前置权限、停止和回滚条件；仅把已有执行证据的动作列为“已采取”；跟踪时间线，恢复必须有核验证据。
4. **无责复盘**：重建时间线，做根因与5 Whys分析，聚焦系统/流程而非指责个人；给出有负责人、优先级与期限的后续建议。

## 严重度参考

| 等级 | 影响参考                     | 响应目标参考       |
| ---- | ---------------------------- | ------------------ |
| SEV1 | 服务中断、所有用户受影响     | 立即响应，全员协同 |
| SEV2 | 主要功能退化、许多用户受影响 | 15分钟内           |
| SEV3 | 次要功能异常、部分用户受影响 | 1小时内            |
| SEV4 | 外观或低影响问题             | 下一工作日         |

这些是上游参考，不是Partner-W自动承诺的SLA；优先使用事故所属团队既有规则。

## 状态更新草稿

标题、SEV等级、状态（调查中/已定位/观察中/已恢复）、影响、最后更新时间。

- 当前已知情况与证据。
- 已采取行动：仅记录真实执行者和结果。
- 下一步建议、负责人、预计下次更新时间；不能估计则明确未知。
- 时间线表：带时区的时间 / 事件 / 来源。

## 无责复盘草稿

日期、持续时长、严重度、作者、草稿状态；用2–3句描述事件。

- 影响：用户/系统、持续时间、可量化业务影响及其来源。
- 时间线：时间（统一时区）/事件/证据。
- 根因：说明因果链、待验证假设和证据缺口。
- 5 Whys：从症状逐步追问成因，证据不足时停止，不为凑五次编造原因。
- 做得好的部分、做得不好的部分、团队经验。
- 行动项：事项 / 负责人 / P0-P2优先级 / 截止日期 / 验收办法。

## 证据边界

监控、告警、事故系统或聊天记录只能通过当前实际可用且已授权的渠道读取。没有连接时依据提供的日志与材料产出草稿；“恢复”与“已通知”必须有真实证据。

## 执行与交付边界

不改变现有权限、工具审批、工作区和文件产物合同。技能是工作流程，不是额外工具、连接或执行授权；只使用当前实际可用且在任务授权范围内的工具与资料。没有连接器时使用本地或用户提供的材料，不宣称平台已接通。
发布、部署、生产处置与对外通知仅输出建议清单或草稿；本技能不默许执行，也不自动创建工单、通知他人或后台监控。实际执行须由获授权的流程另行处理。
需要文件交付时沿现有能力生成并写入允许位置，校验 → 登记 artifact → 用户能打开 才算成功；未保存的文本称草稿，未跑的验证标 NOT RUN，不虚报完成。
