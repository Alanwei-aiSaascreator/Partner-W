      ### 证据（三条都是实测）

      1. `git ls-files --eol`：文本文件 **索引里全是 `i/lf`**，工作区 621 个是 `w/crlf`。
      2. 直接把 blob 抠出来数 CR：`git cat-file blob HEAD:website/tsconfig.json`
         → **CR 0 个、LF 16 个** ⇒ **仓库存的就是纯 LF**。
      3. `git check-attr text eol` → `unspecified` ⇒ **没有 `.gitattributes`**。

      ⇒ 成因链：`core.autocrlf=true`（**本机 git 配置**）在 checkout 时把 LF 转成 CRLF，
      而 `.prettierrc` 写着 `endOfLine: "lf"` ⇒ 两者打架，输的是工作区。
      ⇒ **仓库内容、CI 都没问题**：`.github/workflows/pr-check.yml` 跑在 **ubuntu-latest** 上，
      Linux 上 checkout 出来就是 LF ⇒ **`pnpm format:check` 在 CI 里是绿的**。

      ### 为什么我**没有**动（这是刻意的）

      - 它不是缺陷 ⇒ 没有紧迫性。
      - 根治办法是加 `.gitattributes`（`* text=auto eol=lf`，索引已是 LF ⇒ **零内容改动**）。
        但它**改的是每个人 checkout 的行为**，加完那 621 个 CRLF 文件会先显示成"已修改"，
        直到重新 checkout —— 正是队列警告的"整仓 diff 炸开"那种扰动。
      - `.gitignore` 这类仓库级配置文件你明确留给自己 ⇒ `.gitattributes` 同族，**等你拍板**。
      - 本地跑 `prettier --write .` 只能治一次：下次 checkout 又变回来 ⇒ 是白工，不做。

3. 先给 FTS 喂一份"中文字间插空格"的文本（改 tokenizer 或加冗余列）——

## 🔧 队列外补做的第三项：认下 `run_status` 的**重试相位**（`8142cd6`）

又是一次"扫运行时闭集词表"的收获 —— 这个手法到现在已经产出 **3 个真缺陷**

### 发现

网关在**重试**时发 `run_status` 的**第 8 个相位**，我们此前不认：


⚠️ 而 `server-chat.ts` 的 **chat 投影会把它改写成 `phase:"starting_model"`** ——
所以只有 **agent 流**上是原样的 `retrying`，**正好是我们消费的那条**。

⇒ 症状：网络抖动触发重试时，活动条退回泛化的「正在准备…」，用户看不出
"它在重试、而且已经试到第 2 次了"。

⭐ **数字是这句话的全部价值** —— "正在重试…"几乎等于"正在准备…"，

两条刻意规则：**相位不是重试时一定清掉数字**（否则「正在准备（第 2/4 次）」是确定的错）；

## 🔧 队列外补做的第四项：`lifecycle.finishing` 的显式护栏（`48c7f62`）

同一手法（扫运行时闭集词表）的第四个收获 —— 但这一条的**性质不同**：
前三条是"我们漏接了 / 接错了"，这一条是**"我们碰巧接对了，但没有护栏"**。

### 发现

`lifecycle` 有一个我们不认识的相位，而它是个**陷阱**：

```js
// src/agents/command/lifecycle.ts —— 终态联合
const emitTerminalPhase = (phase: "finishing" | "end" | "error", …) => …

// src/agents/embedded-agent-runner/run/attempt-stream-prepare.ts
terminalLifecyclePhase: attempt.deferTerminalLifecycle ? "finishing" : "end"
```

⇒ **`finishing` 是 `end` 的替代品**，在**还有后续尝试**时发。网关注释：
「Finishing is an **attempt fence**, not the outer execution's final publication」。

### 为什么值得单独一刀（**零行为变更**）

它走 `default` ⇒ 只记 `lifecycle.unknown`、**不改状态** ⇒ 行为是对的。
但后人看到日志里 `lifecycle.unknown {phase:"finishing"}`，
**最自然的"修复"就是照着 `end` 补一个 case** —— 那会在 agent 还在干活时
`setProcessing(false)` + 清 run phase ⇒ **活动条提前消失，用户以为它做完了**。

⇒ 把"我知道它、我故意不处理"写进代码：显式 case + 自己的遥测事件 + 注释写明为什么必须不动。

✅ RED 先行（"记成自己的事件"那条红；两条"不许改状态"**本来就绿** —— 这正是本刀的诚实结论）；
**变异 4/4 全抓住**（含"把它当 end"那条）。core 511（+5）全绿。

### ⭐⭐ 两条**方法论**教训（比这一刀本身值钱）

1. **它此前没被处理的真正原因在类型上**：`AgentLifecycleData.phase` 是个**封闭联合**
   （6 个值），把"我们认得的值"声明成已经齐了 ⇒ 那个 switch 的穷尽性检查
   **反而挡住**了加 `case 'finishing'`（TS2678 就是这么报出来的）⇒ 只能走 `default`。
   ⇒ **"我们认得的值"不要写成封闭联合，除非有东西能保证它真的闭。**
   （网关那边 `phase` 在协议里是开放字符串 —— 闭的只是我们自己的认知。）
2. **"我们以为自己知道全集"这两个月已经栽了三次**：
   ① lifecycle 漏 `fallback_step`/`fallback_cleared`（当时**没有 default** ⇒ 静默）；
   ② `run_status` 漏 `retrying`（这次）；
   ③ 这次：类型把词表**声明成闭的**，反而挡住了补充。
   ⇒ 三次的形状不同、根因同一个。**从运行时枚举发射点**（本轮用的手法）是目前唯一靠得住的做法。
