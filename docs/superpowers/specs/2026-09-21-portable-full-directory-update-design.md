# Partner-W U 盘整目录远程更新设计

**日期：** 2026-09-21

**状态：** 已获用户批准

**适用范围：** Windows U 盘便携交付版

**目标基线：** `fix/local-credential-exposure`（设计时 HEAD `6462d74c`）

## 1. 背景与结论

Partner-W的便携交付物不仅包含 Electron 的 `app.asar`，还包含位于其外部的 OpenClaw 运行时。只替换 `app.asar` 无法同步运行时，也不能可靠修复启动、网关和模型准备链上的问题。因此，便携版更新必须替换完整程序目录，同时严格保留盘上的运行数据和工作区。

本设计采用以下已经批准的方案：

- 使用一个位于程序目录外、源码可审查、可自动测试的小型 Windows 启动器 EXE；
- 应用运行期间在后台下载、校验并解压完整程序包；
- 用户确认“重启更新”后，应用退出，由启动器在同一盘符内交换完整程序目录；
- 新版本通过基础健康检查后才提交更新；
- 交换中断或新版本无法启动时自动恢复上一版本；
- `Partner-W-运行数据`和`Partner-W工作区`永远不属于更新目标。

现有 `packages/desktop/src/main/update/portable-swap.ts` 已具备单文件暂存、备份、恢复和最终确认的基础语义。实施时应复用这些已验证的原则，但不能把目录直接传给当前单文件实现。整目录更新需要独立、边界清晰的目录交换器和逐文件验证器。

> ⚠️ 2026-09-23 更新：`portable-swap.ts` 已于 `21e4c559` 删除（单文件时代的死代码，零生产引用；`runtime/portable-app-data.ts:51` 留了指针）。本文要复用的是其中的**原则**，不是那个文件本身。

## 2. 目标与非目标

### 2.1 目标

1. 用户把压缩包解压到 U 盘后，只需要双击一个固定入口即可启动。
2. 后续版本可以后台下载，准备完成后由用户决定何时重启更新。
3. 真正执行更新时只做同盘目录改名和启动验证，避免再次等待大型运行时解压。
4. 更新失败、断电、拔盘或文件损坏时，盘上始终至少保留一个可恢复的程序版本。
5. 更新不需要管理员权限，不运行安装向导，不向电脑系统目录安装文件。
6. 更新包可验证发布者身份、内容完整性、目标版本和兼容性。
7. 错误必须可区分、可操作，不能统一显示“操作没成功”。

### 2.2 非目标

- 第一版不远程更新启动器自身；
- 第一版不做强制更新；
- 第一版不支持用户主动降级到任意历史版本；
- 第一版不保留多个历史版本，只保留最近一个可回滚版本；
- 第一版不把登录、许可证、网关或模型连接成功作为更新健康条件；
- 本设计不改变“一号一盘”、聊天数据分区或团队 Agent 的产品规则；
- 本设计不实现联网搜索、文生图或视频能力。

## 3. 交付目录

新的便携包采用固定布局：

```text
<盘根>\
├─ Partner-W启动器.exe
├─ Partner-W\
│  ├─ Partner-W.exe
│  └─ resources\<应用与运行时文件>
├─ .Partner-W更新\
│  ├─ update-state.json
│  ├─ update.lock
│  ├─ download\
│  ├─ staged\
│  ├─ backup\
│  └─ logs\
├─ Partner-W-运行数据\
└─ Partner-W工作区\
```

约束如下：

- `Partner-W启动器.exe` 是用户唯一推荐入口，位于可替换程序目录之外；
- `Partner-W\` 是唯一的当前程序目录；
- `.Partner-W更新\` 只存放更新状态、下载、暂存、单份备份和脱敏日志；
- 运行数据和工作区是程序目录的同级目录，任何更新操作都不得把它们作为源、目标或清理范围；
- 所有暂存与备份必须位于同一盘符，确保最终目录交换不依赖跨卷复制；
- 旧 `.bat` 启动器不再作为交付入口。新的 EXE 启动器必须有源码和测试，两者不是同一机制。

现有交付审计中关于“不需要任何启动器”的规则会被本设计取代。实施时必须同步更新交付审计和说明书，使它们要求新的 EXE 启动器，同时继续禁止旧 `.bat`。

## 4. 组件边界

### 4.1 更新检查器

运行在 Electron 主进程，负责：

- 从正式或测试更新源获取签名清单；
- 验证清单签名、渠道、版本和启动器兼容性；
- 向渲染进程发布无密、最小化的更新状态；
- 安排后台下载和准备；
- 不直接交换正在运行的程序目录。

### 4.2 下载与准备器

运行在 Electron 主进程，负责：

- 下载完整程序压缩包到同盘 `.part` 文件；
- 报告进度并支持安全重试；
- 验证压缩包长度和 SHA-256；
- 安全解压到版本隔离的暂存目录；
- 按签名文件清单逐项复核路径、类型、大小和 SHA-256；
- 校验程序 EXE、应用版本、运行时清单等交付指纹；
- 全部通过后写入 `ready` 状态。

### 4.3 目录交换器

由外置启动器调用，负责：

- 获取排他锁并拒绝并发交换；
- 启动前恢复上一次中断的交换；
- 把当前程序目录改名为备份目录；
- 把已验证暂存目录改名为正式程序目录；
- 启动新版本并等待健康确认；
- 在失败时恢复备份；
- 在成功后提交新版本并清理过期暂存。

目录交换器不得拥有下载、网络或业务登录逻辑。

### 4.4 健康确认器

由新版本应用在启动早期执行，负责确认：

1. 正在运行的版本与目标版本一致；
2. 程序路径符合便携布局；
3. 运行数据和工作区路径保护检查通过；
4. 本地数据库能够打开；
5. 必要 IPC 已注册；
6. 主窗口和渲染进程完成一次握手。

以上条件通过后，应用原子写入带交换事务 ID 的健康文件。网络、账号、许可证、网关和模型可能因为外部条件失败，不得阻止健康确认；这些故障由各自状态机和界面处理。

### 4.5 更新界面

渲染进程只展示主进程提供的类型化状态并发送用户意图。它不读取任意路径、不持有签名材料、不执行文件替换，也不自行推断更新成功。

## 5. 服务端清单与信任模型

更新源继续使用：

```text
https://api.rongyinghudong.com/updates/
```

便携版发布一份独立签名清单。逻辑字段如下：

```json
{
  "schemaVersion": 1,
  "channel": "internal",
  "version": "0.0.26",
  "minLauncherVersion": "1.0.0",
  "packageUrl": "https://api.rongyinghudong.com/updates/internal/0.0.26/portable.zip",
  "packageSize": 123456789,
  "packageSha256": "<64-character-lowercase-hex>",
  "fileManifestSha256": "<64-character-lowercase-hex>",
  "publishedAt": "2026-09-21T00:00:00Z",
  "mandatory": false,
  "signature": "<base64-ed25519-signature>"
}
```

签名规则：

- 使用 Ed25519；
- 私钥只存在于受控发布环境或 CI 密钥库，不进入仓库、客户端或更新包；
- 公钥嵌入应用和启动器；
- 对去掉 `signature` 字段后的 RFC 8785 规范化 JSON UTF-8 字节签名；
- 客户端先验证清单签名，再相信下载 URL、版本、哈希和文件清单；
- HTTPS、签名和哈希必须同时通过；
- `schemaVersion: 1` 要求 `mandatory` 为 `false`，出现不支持的强制策略时客户端拒绝安装并提示升级基础包。

SHA-256 只能证明下载内容与清单一致，不能证明清单来自Partner-W。数字签名是发布者真实性的必要条件。

## 6. 压缩包安全规则

在写出解压文件之前，准备器必须检查归档目录。以下任一情况都应拒绝整个包：

- 绝对路径、盘符路径、UNC 路径；
- `..` 路径穿越、空路径或规范化后越出暂存根目录；
- 符号链接、junction、硬链接或其他 reparse point；
- 重复规范化路径、大小写碰撞或 Windows 保留设备名；
- 包含 `Partner-W-运行数据`、`Partner-W工作区`、`.Partner-W更新`或外置启动器；
- 未列在签名文件清单中的额外文件；
- 清单列出的文件缺失、大小不符或哈希不符；
- 可执行文件、应用版本或运行时清单不符合目标版本。

解压与验证只能在新建的版本隔离目录中进行。验证失败时只清理该事务自己的暂存内容，不得使用宽泛递归路径、未解析变量或通配符清理盘根目录。

## 7. 状态机与持久化

更新状态机为：

```text
idle
  -> checking
  -> downloading
  -> verifying_archive
  -> extracting
  -> verifying_files
  -> ready
  -> applying
  -> awaiting_health
  -> committed

任意准备阶段 -> failed_prepare -> idle/retry
applying/awaiting_health -> rollback_required -> rolled_back
```

`update-state.json` 至少记录：

- 状态 schema 版本；
- 唯一事务 ID；
- 当前版本、目标版本和渠道；
- 下载、暂存、正式目录和备份目录的规范化路径；
- 已验证清单摘要；
- 当前阶段和最后更新时间；
- 最近一次结构化错误码；
- 健康确认期限。

状态文件采用“写临时文件后同目录改名”的方式更新。启动器不能盲信状态文件：每次启动都要把状态与实际目录、版本指纹和事务 ID 交叉检查。文件系统事实优先于陈旧状态。

`update.lock` 通过独占创建获得。锁包含启动器 PID、事务 ID 和创建时间。只有确认进程不存在且状态可恢复时，才能接管陈旧锁。

## 8. 正常更新流程

1. 应用检查签名清单，发现同渠道更高版本。
2. 检查空间。所需空间按“压缩包 + 解压后新目录 + 当前目录备份 + 安全余量”计算。
3. 在后台下载、验证和解压，不阻塞聊天和其他已运行功能。
4. 准备完成后显示“新版本已准备好”，用户选择立即重启或稍后。
5. 立即重启时，应用把已验证事务交给启动器并正常退出。
6. 启动器确认应用相关进程和文件句柄已退出，获取排他锁。
7. 启动器恢复任何旧的未完成事务，然后把当前程序目录改名到备份位置。
8. 启动器把暂存目录改名为正式程序目录。
9. 启动器从新目录启动应用，等待带相同事务 ID 的健康文件。
10. 健康确认成功后，启动器写入 `committed`，保留一份上一版本备份直到下次正常启动，再安全清理。

下载和大型解压均在应用仍可使用时完成。用户确认后的更新窗口不再解压运行时，通常只剩同盘目录改名和一次正常启动。

## 9. 故障恢复

| 故障                 | 处理                                       | 当前版本是否受影响 |
| -------------------- | ------------------------------------------ | ------------------ |
| 检查或下载断网       | 保留 `.part` 或按策略重试，显示网络错误    | 否                 |
| 空间不足             | 下载前阻止；报告所需与可用空间             | 否                 |
| 清单签名失败         | 拒绝并删除该事务下载                       | 否                 |
| 压缩包或文件哈希失败 | 拒绝并删除该事务暂存                       | 否                 |
| 解压中关机或拔盘     | 下次启动识别未完成事务并安全清理或重新准备 | 否                 |
| 当前目录改名后中断   | 下次启动从备份恢复正式目录                 | 可恢复             |
| 新目录就位后中断     | 根据新旧版本指纹与状态继续验证或回滚       | 可恢复             |
| 新应用启动即退出     | 立即回滚备份                               | 自动恢复           |
| 健康确认超时         | 结束尚未进入可用态的新进程并回滚           | 自动恢复           |
| 备份和正式目录都异常 | 停止所有写操作，保留证据并给出人工恢复路径 | 不承诺自动修复     |

恢复算法必须是幂等的：在每个步骤再次断电后，下一次启动仍能重新判断并继续恢复。

## 10. 用户体验与错误契约

界面状态与建议文案：

- `available`：发现新版本，可查看版本说明；
- `downloading`：显示版本、进度、已下载大小和取消入口；
- `preparing`：说明正在校验和准备，应用仍可使用；
- `ready`：显示“版本 X 已准备好，重启后完成更新”；
- `applying`：启动器显示“正在更新，请勿拔出 U 盘”；
- `committed`：显示“已更新到版本 X”；
- `rolled_back`：显示“更新未完成，已恢复到版本 X，现有数据未受影响”。

错误至少分为：

- 网络不可用；
- 更新源响应异常；
- 签名或完整性失败；
- U 盘空间不足；
- U 盘断开或只读；
- 文件被占用；
- 启动器版本不兼容；
- 新版本基础启动失败；
- 恢复失败，需要人工处理。

每种错误都通过共享 DTO 传递稳定错误码和可本地化参数。日志不得记录 Token、密码、授权卡号、用户消息或完整个人路径；用户界面不得显示底层堆栈。

## 11. 版本和发布策略

- 只允许同渠道升级；
- 使用严格 SemVer 比较，默认只接受高于当前版本的版本；
- 用户不能通过远程清单主动降级；
- 自动回滚只回到本次交换前保存的上一版本；
- `minLauncherVersion` 高于当前启动器时拒绝安装，并要求获取新的完整基础包；
- 第一版测试渠道和正式渠道使用不同清单位置；
- 更新包发布后先在测试渠道和真实 U 盘验证，再切换正式清单；
- 每次发布保留服务端清单、签名、包哈希和发布审计记录。

### 11.1 0.0.25 的引导限制

当前便携更新路径仍以“检查后提示手动替换”为主，外置 EXE 启动器尚未成为完整、已验证的交付入口。已有 0.0.25 包不能凭空获得本设计的整目录安全更新能力。

因此必须人工分发一次包含新启动器和新目录布局的完整基础包。只有从这个基础包开始，后续版本才可使用本设计的远程更新链。对外说明不得宣称所有现存 0.0.25 包已经能够自动更新。

## 12. 测试与证据

### 12.1 单元测试

- SemVer、渠道和 `minLauncherVersion` 判定；
- RFC 8785 规范化和 Ed25519 正负样本；
- 状态机合法与非法转换；
- 路径规范化、穿越、大小写碰撞和保留名；
- 错误码到用户动作的映射；
- 空间预算计算。

### 12.2 真实文件集成测试

在临时目录中使用真实文件和目录验证：

- 完整下载、哈希、解压、逐文件验证和目录交换；
- 正式目录、暂存目录、备份目录的每一种存在组合；
- 每个状态落盘点和目录改名点的故障注入；
- 重复恢复的幂等性；
- 新版本健康、早退、超时和错误事务 ID；
- 更新前后运行数据与工作区的摘要完全不变。

### 12.3 打包与真盘验收

- Windows 普通用户，无管理员权限；
- 中文路径和带空格路径；
- exFAT 与 NTFS 各一块真实盘；
- 至少两台没有安装开发环境的 Windows 电脑；
- 断网、下载中断、空间不足、坏签名、坏哈希、文件占用；
- 下载、解压、目录交换和等待健康时分别强制结束进程；
- 在交换阶段安全模拟拔盘或掉电；
- 从测试版本升级、故意失败回滚、再升级到正确版本；
- 更新后登录、聊天、许可证、网关和模型连接分别进行产品验收，但这些业务结果不冒充更新器基础健康证据。

没有真实 U 盘时可以完成代码、单元测试和临时目录集成测试，但真盘项必须保持“未验证”，不能用本地目录测试替代。

### 12.4 测试纪律

每个行为改动先获得按测试名可识别的 RED，再实现 GREEN。变异验证必须证明测试真的执行了目标路径，包含唯一锚点、`passed > 0`、自检变异和脚本自身失败的明确诊断。最终执行项目既有类型、lint、架构、UI 契约、文案、i18n、U 盘交付和 Vitest 门禁。

## 13. 实施与产品优先级

代码可以在等待真盘期间推进，但发布顺序必须服从基础功能：

1. **P0 登录、许可证和模型连接**：账号切换不得永久停在“正在准备模型”；所有等待有上限；授权、网络和网关错误可区分。已部署的生产计费修复仍需一条真实聊天请求验证落账。
2. **P0 便携更新底座**：签名清单、后台准备、外置启动器、整目录交换、恢复、UI 和发布门禁。
3. **P1 团队 Agent 闭环**：点击 Agent 进入正确会话，禁止无声回主罗盘；跨电脑明确区分团队记录与本机 Agent 安装状态；内部英文标识与展示名分离。
4. **P1 官方 MCP 联网搜索**：不可用时明确失败，不能伪装已联网。
5. **P2 文生图与视频**：基础交付稳定后再接入。

远程更新不能成为绕过基础功能验收的理由；基础功能也不能通过手工覆盖程序目录替代更新器故障测试。

## 14. 验收标准

本功能只有同时满足以下条件才可宣称完成：

1. 用户始终从外置 EXE 启动器启动，不需要 `.bat`、安装或管理员权限。
2. 完整程序和 OpenClaw 运行时一起升级，更新目录中没有旧版本残留文件。
3. 更新前后登录数据、聊天、团队数据、运行数据和工作区均不被替换。
4. 下载和解压在后台完成，用户确认后不再等待大型运行时解压。
5. 坏清单、坏包、断网、空间不足和准备阶段拔盘不影响当前版本。
6. 交换阶段中断和新版本启动失败能够恢复上一版本。
7. 更新器错误均有稳定错误码、明确中文提示和可执行下一步。
8. 单元、集成、故障注入、打包和真实 U 盘矩阵均有可追溯证据。
9. 测试渠道演练通过后才修改正式更新清单。
10. 对外明确：现有 0.0.25 包需要一次人工基础包迁移，此后版本才具备完整远程更新能力。
