## 2. 两个必须尊重的约束

1. **不能让助手依赖宿主环境**。网关进程的环境是刻意收缩的：
   `runtime/gateway-process.ts:425-470` —— 摘掉了所有会触发"外置插件自动装"的 API key、
   清掉 `NODE_OPTIONS`/`NODE_PATH`、**保留普通 PATH**。
   随包 Node 在 `deployed/<key>/node/node.exe`，**不一定在 PATH 上**，同事机器也可能根本没装 Node。
   ⇒ 「技能里写个 `node gen.mjs` 让助手跑」这条**不可靠**，不要建在这上面。
2. **产物链已经现成**。`main/artifact/reconcile.ts` 会扫任务目录（深度 4、有预算），
   而且 **MIME 表里已经有 `.pptx`**（第 40 行，type = `file`）
   ⇒ **只要文件被写进任务目录，产物面板就会列出来、用户能打开**。不需要新 UI。

## 3. 推荐设计：**客户端生成**（我们写文件，助手只出内容）

一句话：**助手负责"想"，客户端负责"排"**。

```
用户：帮我做个 PPT
  ↓
助手（技能指导它）把内容写成固定 schema 的请求文件：
   <工作区>/<任务>/docgen/<名字>.docgen.json
  ↓
客户端主进程（完整 Node，库随 App 打包）：
   校验 schema → pptxgenjs 渲染 → 写 <工作区>/<任务>/<名字>.pptx
  ↓
产物面板自动列出来（reconcile.ts 扫任务目录，无需新代码）→ 用户双击打开
```

### 为什么是这条

- **完全离线**：库随 App 走（`app.asar` 里的普通依赖），不碰宿主 PATH、不需要 npm/python。
- **复用现成管道**：技能走 `packages/desktop/our-skills/`（`main/skills/bundled.ts` 装机时自动装，
  已有 `our-skills-bundled.test.ts` + `our-skills-packaging-gate.test.ts` 两道闸）；产物走 `reconcile.ts`。
- **可测**：schema 校验与"请求 → 文件"是纯函数，vitest 直接钉；不需要真跑网关。
- **换库即换格式**：docx / exceljs 是同一套形状，P2 只换渲染器。

| **A3 运行时插件（plugin-skills）** | 机制存在（`plugin-skills/` 有 browser-automation / canvas），但插件格式与装载时机我们没验证过，且要动 `pack-runtime.mjs` 的注入逻辑；可作为 P3 的优化 |

## 6. 风险与边界

- **体积**：`pptxgenjs` 约 1–2MB，docx/exceljs 各 1–3MB。相对当前包体积可忽略，但要在打包闸门里记录。
- **字体**：pptx 只存字体名，由用户机器的 PowerPoint/WPS 渲染 ⇒ 不内嵌字体（也避免授权问题）。
- **质量**：排版好坏取决于 schema 设计 + 技能里的写作规范，**不取决于库**。P1 刻意只做一种版式，先把链路走通。
- **不做**：服务端生成；模板市场；内嵌字体；读取 Office 文件（那是另一条缺口，另行立项）。

## 7. 与同事那份反馈的关系

- 同事的「PPT 有缺陷」在这条方案里**不是 bug 修复**，是补能力；补上之前，**P4 的文案收口应当先做**（否则助手每次都会许一个做不到的愿，用户每次都失望一次）。
- 同一批反馈里的「文生图」是**同一类缺口**（目录里没有任何图像模型），另行决策，不在本方案内。

## 8. ⭐ 追加发现（2026-09-24）：**改动到不了已有盘** —— 这是 P1/P4 的真障碍

动手时才发现：**"把边界/能力写进提示词"解决不了已发出去的盘**。两条可能的通道都不自动更新：

| 通道                                | 实测结论                                                                                                      | 出处                                                      |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 助手提示词（IDENTITY.md / SOUL.md） | **只在文件缺失时才写**；已完整 ⇒ 直接跳过。**没有内容版本概念**                                               | `preset-agent-installer.ts:135`、`if (!identityComplete)` |
| 随包技能（`our-skills/`）           | 写入是**覆盖语义**（"已存在则覆盖，先删旧的再拷"）—— 但**调用点只有用户点「安装」那一个 IPC**，没有开机自动装 | `main/skills/bundled.ts:201`、`handlers.ts:128`           |
| 其余                                | 客户端没有"每次启动重写"的常驻注入点（`setAgentFile` 的调用点全部是安装/用户编辑）                            | 全仓 grep                                                 |

⇒ 后果：

- **P4 的边界**只对**新装**生效（同事那块盘、所有已发出的内测盘都不会变）；
- **P1 的能力**同样到不了已有盘 —— 也就是说 A 方案做完了，**老盘上还是做不到 PPT**。

### 已经落地的两件事（为推送铺路）

1. **交付边界**写进六个预置助手共用的 `COMMON_OPERATING_CONTRACT`
   （`## Delivery boundary`：产不出 `.pptx/.docx/.xlsx`/图片、**不许许诺**、第一句就说明、
   工作区之外不声称能直接拿到）。
2. **版本标记**：预置助手的提示词写入时盖 `<!-- partner-w-prompt:<版本> -->`
   （HTML 注释，markdown 渲染不可见）。**只给内置六个预置盖**——市场模板的内容来自数据库、
   用户还会改，盖我们的版本号会让将来的升级判据把"用户改过的模板"误认成我们的。
   有了标记，将来才能安全地判"是我们写的旧版本 ⇒ 可升级"。

### 还差一个决定：**老盘怎么升级**（三条路，风险不同）

|                 | 做法                                                                                   | 风险                                                                          |
| --------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **甲** 保守     | 老盘一律不碰；将来给一个显式的「恢复默认提示词」入口                                   | 最安全，但 A 的能力对已发出的盘**永远不生效**                                 |
| **乙** 指纹采纳 | 盘上文件若与**我们历史上发过的某一版**逐字节相同 ⇒ 判为未被改动 ⇒ 升级；不匹配一律不碰 | 精准且安全；代价是要保留历史版本指纹（构建期从 git 历史算，或首次发布时固化） |
| **丙** 技能通道 | 把边界/能力放进**技能**并加"开机刷新随包技能"                                          | 技能是**按需加载**的，"不许许诺"这种常驻约束放技能里**管不住**；只适合放能力  |

**建议乙**（配合已落地的标记：新盘走标记，老盘走指纹），并把"丙"作为 P1 技能的常规更新通道。

## 9. P1 落地记录（2026-09-24，提交 `4e4d24f6`）

**分工**：助手在回复里给出一个 ` ```docgen ` 块（JSON：标题/副标题/每页标题+要点+备注），
客户端主进程用 pptxgenjs 渲染成真 `.pptx`，再走**现成的产物通道**

### 为什么把通道从"文件"改成"消息"（§3 的流程图已作废，以此节为准）

§3 原设计是"助手写请求文件、客户端扫任务目录"。**做不到**：助手沙箱限在**它自己的工作区**
（`<root>/partner-w-agents/<agentId>`），客户端的产物通道要的是**任务目录**（`<root>/<taskId>`）——
两者是**兄弟目录**，助手写不过去（同事那条 `exec 列出桌面…` 失败就是同一沙箱边界的另一面）。
而且"助手的工作目录到底是哪个"是**没验证过的运行时事实**。

消息是**已经验证过**的通道（`artifact/extract.ts` 本来就从消息里抽代码块与图片）。
改走消息后，沙箱、cwd、PATH 全都不参与 ⇒ 方案对宿主环境的依赖降到零。

### 一并改的

- `artifact/extract.ts`：代码块抽取跳过 `docgen`（否则产物里会多一段 JSON 噪音）。
- `artifact/save.ts`：补 Office 的 MIME（原来只有 reconcile 那张表有 `.pptx`）。
- `MarkdownContent.tsx`：`docgen` 块渲染成一行卡片（"成品见右侧产物"），不摊 JSON。
- `COMMON_OPERATING_CONTRACT`：pptx 从"做不到"改成**有条件的可能**（技能可见时才承诺），
  docx/xlsx/图片仍然做不到；新增**"不许说文件已经存在"**（客户端在这一轮结束后才渲染）。
