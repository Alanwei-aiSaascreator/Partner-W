## 2. 两个必须尊重的约束

1. **不能让助手依赖宿主环境**。网关进程的环境是刻意收缩的：
   `runtime/gateway-process.ts:425-470` —— 摘掉了所有会触发"外置插件自动装"的 API key、
   清掉 `NODE_OPTIONS`/`NODE_PATH`、**保留普通 PATH**。
   随包 Node 在 `deployed/<key>/node/node.exe`，**不一定在 PATH 上**，同事机器也可能根本没装 Node。
   ⇒ 「技能里写个 `node gen.mjs` 让助手跑」这条**不可靠**，不要建在这上面。
2. **产物链已经现成**。`main/artifact/reconcile.ts` 会扫任务目录（深度 4、有预算），
   而且 **MIME 表里已经有 `.pptx`**（第 40 行，type = `file`）
   ⇒ **只要文件被写进任务目录，产物面板就会列出来、用户能打开**。不需要新 UI。

## 3. 推荐设计：**客户端生成**（我们写文件，助手只出内容）

一句话：**助手负责"想"，客户端负责"排"**。

```
用户：帮我做个 PPT
  ↓
助手（技能指导它）把内容写成固定 schema 的请求文件：
   <工作区>/<任务>/docgen/<名字>.docgen.json
  ↓
客户端主进程（完整 Node，库随 App 打包）：
   校验 schema → pptxgenjs 渲染 → 写 <工作区>/<任务>/<名字>.pptx
  ↓
产物面板自动列出来（reconcile.ts 扫任务目录，无需新代码）→ 用户双击打开
```

### 为什么是这条

- **完全离线**：库随 App 走（`app.asar` 里的普通依赖），不碰宿主 PATH、不需要 npm/python。
- **复用现成管道**：技能走 `packages/desktop/our-skills/`（`main/skills/bundled.ts` 装机时自动装，
  已有 `our-skills-bundled.test.ts` + `our-skills-packaging-gate.test.ts` 两道闸）；产物走 `reconcile.ts`。
- **可测**：schema 校验与"请求 → 文件"是纯函数，vitest 直接钉；不需要真跑网关。
- **换库即换格式**：docx / exceljs 是同一套形状，P2 只换渲染器。

### 备选（不推荐，留档）

| 方案                               | 为什么不选                                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A1 注入库 + 让助手跑脚本**       | 依赖 `exec` 能拿到 node —— 约束 1 说它不可靠；且模型手写脚本每次都可能不一样，失败面大                                                                |
| **A3 运行时插件（plugin-skills）** | 机制存在（`plugin-skills/` 有 browser-automation / canvas），但插件格式与装载时机我们没验证过，且要动 `pack-runtime.mjs` 的注入逻辑；可作为 P3 的优化 |
| **B 服务端生成**                   | 用户已排除：离线盘用不了，且要设计计费                                                                                                                |

## 5. 分阶段

| 阶段   | 内容                                                                                       | 验收口径                                                                                              |
| ------ | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| **P1** | pptx：封面 + 标题/要点页（一种版式）；技能（含请求 schema 与"别先许诺"的约束）；产物链打通 | 真机：说"做个 PPT" → 任务目录出现 `.pptx` → 产物面板可见 → **双击能用 PowerPoint/WPS 打开且内容正确** |
| **P2** | docx / xlsx 同构接入（换渲染器）                                                           | 同上，三种格式各一遍                                                                                  |
| **P3** | 版式与模板（品牌色、公司模板）、"把当前对话整理成 PPT"入口                                 | 模板可换且不改代码                                                                                    |
| **P4** | 文案收口：只有**真能出**的格式才在技能/助手自述里许诺（与 C 方案合流）                     | 全库搜不到"我给你出个 PPT"这类无能力承诺                                                              |

## 6. 风险与边界

- **体积**：`pptxgenjs` 约 1–2MB，docx/exceljs 各 1–3MB。相对当前包体积可忽略，但要在打包闸门里记录。
- **字体**：pptx 只存字体名，由用户机器的 PowerPoint/WPS 渲染 ⇒ 不内嵌字体（也避免授权问题）。
- **质量**：排版好坏取决于 schema 设计 + 技能里的写作规范，**不取决于库**。P1 刻意只做一种版式，先把链路走通。
- **不做**：服务端生成；模板市场；内嵌字体；读取 Office 文件（那是另一条缺口，另行立项）。

## 7. 与同事那份反馈的关系

- 同事的「PPT 有缺陷」在这条方案里**不是 bug 修复**，是补能力；补上之前，**P4 的文案收口应当先做**（否则助手每次都会许一个做不到的愿，用户每次都失望一次）。
- 同一批反馈里的「文生图」是**同一类缺口**（目录里没有任何图像模型），另行决策，不在本方案内。
