# 荣盈魔方 U 盘整目录更新发布基础设施纠偏设计

**日期：** 2026-09-22

**状态：** 待用户复审（V2 原则已通过；首版纳入五项强制修订，第二版已纳入 Codex 独立复核的六项修正）

**适用范围：** Windows U 盘便携交付版的发布基础设施——生产密钥、启动器来源核对、feed 上传、CI 边界与相关文档

**目标基线：** `fix/local-credential-exposure`（撰写时 HEAD `576af78c`）

## 1. 背景与结论

### 1.1 为什么需要这份设计

整目录远程更新的**代码**已经完成（Task 1–12，HEAD `576af78c`），但**发布基础设施**还没有成型：

- 没有生产 Ed25519 密钥，也没有密钥生成或备案流程；
- 上游 GitHub Actions 无法为本产品运行（`origin` 是 Gitee，GitHub 上游是只读的公开仓）；
- 仓库里**没有任何经过审计的 feed 上传工具**；
- 交付审计对启动器**只检查“文件存在且前两字节是 `MZ`”**；
- 兼容性门禁 `minLauncherVersion` **只有一侧在查，而且查的是硬编码常量**。

本设计只修**发布基础设施**，不改动已经验收的更新客户端机制。

### 1.2 决定方案形状的已核实事实

以下每条都来自只读侦察，可复查：

1. **启动器不可自我更新。** 它位于 U 盘盘根，不在被替换的 `荣盈魔方/` 程序目录内，`launcher/internal/update/swap.go` 全程不处理它。它是**永久信任锚**。
2. **两侧各自独立验签、各自内嵌公钥。** 启动器经 `-ldflags -X main.publicKeyBase64=` 注入（`scripts/lib/portable-launcher-build.mjs:49`）；应用经 `__MOFANG_UPDATE_PUBLIC_KEY_B64__` 注入（`packages/desktop/electron.vite.config.ts:10`）。
3. **两侧都是严格解码。** `DecodeSignedManifest` 与 `DecodeFileManifest` 都使用 `DisallowUnknownFields()`（`launcher/internal/update/model.go:102-113, 129, 141`）。⇒ **给 manifest 增加任何字段，都会让已经出厂的启动器整条拒收**（`ErrManifestInvalid`）。
4. **因此密钥信任模型只能在第一把出厂启动器里定死。** 目前**一把启动器都还没有出厂**：线上 `/updates/` 只有安装器（最新 `0.0.23`），`/updates/internal/manifest.json` 与 `/updates/stable/manifest.json` 均为 404，`0.0.25` 不带外置启动器。**这个窗口是开的，也是唯一的。**
5. **manifest 只有一个绝对 URL 字段 `packageUrl`**（`scripts/lib/portable-update-release.mjs:416`，经 `new URL` 构造、强制 https、路径为 `<base>/<channel>/<version>/portable.zip`）。**没有 `fileManifestUrl`**；客户端用 `new URL('portable-files.json', packageUrl)` 做兄弟解析（`packages/desktop/src/main/ipc/update-handlers.ts:92`）。⇒ **版本目录必须同时包含 `portable.zip` 与 `portable-files.json`。**
6. **客户端有防降级。** `manifest.version <= currentVersion` 直接判为“已是最新”（`packages/desktop/src/main/update/portable-manifest.ts:140`）。
7. **服务端可用原语：** 有 `sha256sum`、`scp`、`sftp`；**没有 `rsync`**。`/opt/rongying/updates` 与 `/opt/rongying/backups` 均为 `root:root 755`，同处 `/dev/vda3`。可用空间约 25.8 GB。
8. **nginx：** `location /updates/ { alias /opt/rongying/updates/; autoindex off; }` 为前缀匹配（子目录可服务）；`no-cache` 只挂在精确路径 `= /updates/latest.yml` 上。

### 1.3 结论摘要

采用**方案一**：单一离线生产钥匙 + 真实启动器版本双重门禁 + 可恢复的人工上传器。

本设计**明确不提供**密钥撤销、安全轮换与操作系统级代码签名；这三项要么是方案二的课题，要么依赖外部证书，均在本文件中如实记录为已知缺口。

## 2. 目标与非目标

### 2.1 目标

1. 定义生产密钥的完整生命周期，并诚实地说明丢失与泄露的后果。
2. 修复三个与启动器版本有关的真实缺陷，使 `minLauncherVersion` 成为**真实**的双重门禁。
3. 让启动器具备**防配错与来源核对材料**（属于审计元数据，**不是**可信来源证明）与**运行时功能挑战**。
4. 提供一个**可恢复、可审计、可并发控制**的人工 feed 上传器设计。
5. 明确 CI 的能力边界：CI 绝不产出生产签名 manifest。
6. 纠正文档中已知的错误描述与错误口径。

### 2.2 非目标

- 不修改更新客户端已有的下载、解压、验树、交换、回滚与健康回执机制。
- 不实现密钥撤销、信任策略、epoch 或防回滚状态（方案二，单独立项）。
- 不实现服务端受限发布账号与目录属主改造（方案二范围内的加固）。
- 不采购或接入 Authenticode 代码签名证书。
- 不在本设计中给出实现代码、构建产物、生产密钥或任何服务器写操作。

## 3. 生产密钥生命周期

### 3.1 形态

**一把长期生产 Ed25519 私钥，严格离线保存。** 启动器与应用嵌入**同一把**公钥。发布时临时解密完成签名，会话结束后立即删除临时文件。

### 3.2 后果（必须如实承认）

| 事件     | 后果                                                                       | 处置                                                                                        |
| -------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 私钥丢失 | 无法再签任何新版本，**只能停发更新**。已发出去的盘照常运行，冻结在最后版本 | 从离线备份恢复；备份也失效时，只能靠人工更换基础包重启发布能力                              |
| 私钥泄露 | 持有者可为任意版本签名。**没有任何机制能撤销它**                           | **必须人工更换基础包**（新钥匙 + 新启动器）。在更换完成之前，所有旧盘仍然信任那把泄露的钥匙 |
| 算法迁移 | 同泄露处置                                                                 | 人工更换基础包                                                                              |

⇒ **本设计不提供“安全轮换”。** 只有“停发”与“人工更换基础包”两种结局。

### 3.3 为什么不做预置多把等权钥匙

1. **等权钥匙不提供撤销。** 备用私钥泄露与现役私钥泄露同样致命。
2. **它让发现更难。** 没有 keyId 时，从签名上看不出是哪把钥匙签的。
3. **它把保管负担乘以钥匙把数**，与“单一离线生产钥匙”的目标相反。
4. 把它描述为“安全轮换”是错误的：那是多把同样受信任的钥匙，既不是轮换，也不是撤销。

### 3.4 keyId 的定位

- keyId **可以本地人工签名实现，不依赖 GitHub 或 CI**。
- 但 **keyId 本身不提供撤销**。它只给钥匙命名，让人能说出“这是哪把签的”。撤销需要**信任策略**（根钥匙签发策略文件、epoch 或防回滚状态），属于方案二。
- 由于 §1.2 第 3 条（严格解码），**给 manifest 增加 keyId 字段会让所有在役启动器整条拒收** ⇒ keyId **只能是第一把启动器就带的选择，不能后补**。
- ⇒ keyId 归入方案二，**不与方案一混做**。

### 3.5 生命周期逐项

| 环节     | 规则                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 生成     | 离线机器、断网、一次性。Ed25519；私钥 PKCS#8 PEM，公钥 SPKI DER Base64                                           |
| 指纹     | `SHA-256(SPKI DER)`，以大写 hex 分组显示                                                                         |
| 备案     | 仓库 `docs/` 内维护**公开**密钥台账：keyId、指纹、用途、生成日期、状态、对应启动器最低版本。**只记录公钥与指纹** |
| 离线保存 | 私钥两份、异地保存、介质加密。**严禁**进入仓库、GitHub、Gitee（含 secret）、任何服务器、日志、客户包、CI 日志    |
| 临时解密 | 仅在发起签名的机器；受限权限临时文件；会话结束立即删除；会话记录只写**指纹**，不写钥匙本体                       |
| 备份     | 丢失即停发，因此备份必须真实可用，并**定期演练恢复**（恢复后签一条并验证，再销毁演练产物）                       |
| 销毁     | 仅当所有已发出的盘都已更换为不再信任该钥匙的新基础包之后；销毁须留凭据（执行人、时间、机器、介质处置方式）       |
| 轮换     | 不存在安全轮换，只有定期或事件驱动的**人工更换基础包**                                                           |

指纹是哈希，可以进入日志与仓库；现有 `redactSecrets` 保护的是原始钥匙串，两者不冲突。

### 3.6 Windows 上的私钥处理

1. 私钥存放在**加密卷**上（如 VeraCrypt 容器或 BitLocker To Go 介质），不放在系统盘普通目录。
2. 签名会话期间解密挂载到**最小权限临时目录**，并**显式设置 NTFS ACL**：中断继承，仅授予执行签名操作的那个账号（例如 `icacls <dir> /inheritance:r /grant:r "<account>:(OI)(CI)F"`）。
3. 会话结束立即删除临时文件并卸载卷。
4. **不得承诺取证级擦除。** 在带磨损均衡与 TRIM 的 SSD 上，覆盖写或普通删除**都不能可靠清除**先前副本；文件内容还可能残留在卷影副本、页面文件与休眠文件中。因此本设计**不声称 shred 能力**，实际依赖的是：卷级加密、把暴露窗口压到最短、ACL 限制、以及及时删除。
5. 若确实需要取证级保证，那属于另一个威胁模型，结论应是改用硬件令牌或 HSM，而不是继续用文件。
6. 具体纪律：不把私钥粘贴到会被记录的终端、不使用带备份或交换文件的编辑器、不进入 shell 历史。

## 4. 必须与发布基础设施同批修复的真实缺陷

### 4.1 应用侧用硬编码常量冒充启动器版本

`packages/desktop/src/main/ipc/update-handlers.ts:28` 定义 `const LAUNCHER_PROTOCOL_VERSION = '1.0.0';`，并在 `:83` 把它作为 `launcherVersion` 传入 manifest 门禁。于是 `packages/desktop/src/main/update/portable-manifest.ts:137` 的 `minLauncherVersion` 比较**比的是这个常量，而不是盘上那个启动器的真实版本**。该常量只会**高估**能力，永不低估。

**要求：** 应用必须**执行盘根启动器读取真实版本**，并满足：

- 带**超时**；超时即拒绝，不得阻塞启动；
- 输出必须是**严格 SemVer**；不符合即拒绝；
- 启动器缺失、无法执行、退出码非零、输出不可解析等**任何失败一律拒绝更新**（fail-closed），**绝不回退到常量**。

启动器侧已具备读取真实版本的代码路径：`launcher/cmd/mofang-launcher/main.go:52-54` 解析 `--version`，`:133-136` 打印由 `-X main.version` 注入的真实构建版本。

**应用统一使用哪个通道（避免两条路径并存）：** 应用**统一调用 `--describe-json`**（见 §5.7），在一次调用中同时取得真实版本与嵌入公钥指纹，并受 `schemaVersion` 契约约束。`--version` 保留给人工与脚本使用，**不作为应用侧门禁的取值来源**。

**GUI 子系统 stdout 实验结论（已完成）：** 使用 Node `child_process.execFile` 调用当前的 `artifacts/荣盈魔方启动器.exe --version`，实测得到 **exit 0**，stdout 为 **`"0.1.0\n"`**。⇒ Node/Electron 父进程捕获 GUI 启动器 stdout 的**技术路径已被当前二进制初步证实**。

- 仍需在实现 `--describe-json` 之后，为**同一路径**补一条自动化测试（当前证据只覆盖 `--version` 与这个二进制）。
- **暂不引入 `--out` 临时文件协议**，除非后续测试证明 stdout 不稳定。这是把复杂度留到有证据时再引入。

### 4.2 Go 启动器完全不校验 `minLauncherVersion`

在整个 `launcher/` 树中，该字段只出现于结构体定义（`launcher/internal/update/model.go:53`）、签名载荷（`launcher/internal/update/verify.go:115`）与测试夹具（`launcher/testdata/manifest.json:5`）。**它被签名，但从不被执行。** 兼容性门禁只有应用一侧在查，而应用查的是常量。

**要求：** 启动器在**执行交换之前**，用自己**编译进去的真实版本**再次比较 `manifest.minLauncherVersion`；不满足即拒绝交换。这是纵深防御，不替代应用侧门禁。

### 4.3 删除 `LAUNCHER_PROTOCOL_VERSION`

它是**协议版本**，不是启动器版本。两者混用正是 §4.1 的成因。删除后不得以任何其他常量形式重新引入“假装是启动器版本”的值。

### 4.4 双重门禁的能力边界

修复 §4.1 与 §4.2 之后，才存在真正的双重门禁：应用侧读**真实版本**把关，启动器侧**自检真实版本**把关，两侧独立。

⚠️ **`minLauncherVersion` 仅用于兼容性门禁。不得宣称它能撤销已泄露的签名密钥。** 它拦的是“启动器太老”，不是“签名者不可信”。

## 5. 启动器来源核对：防配错与可审计

### 5.1 定位（不可升格）

构建回执**始终只是防配错与审计元数据**。在引入 Authenticode 或受信任的 attestation 之前，**不得**把它称为可信来源证明。任何人都能伪造一份回执，它不能证明“这个二进制是谁构建的”。

它真正能做的三件事：

1. 发现**配错**：拿错 EXE、烧错公钥、版本对不上；
2. 提供**审计线索**：这次构建声称了什么、由哪次提交产生；
3. 让**静态与运行时检查**有可对照的预期值。

### 5.2 构建侧

- 新增显式 `--out <空目录>`；默认输出路径只保留给开发使用。
  现状：构建 CLI **没有 `--out`**，输出路径写死为 `<repo>/artifacts/荣盈魔方启动器.exe` 且**静默覆盖**（`scripts/lib/portable-launcher-build.mjs:10, 66`；入口 `scripts/build-portable-launcher.mjs` 不传 `outputPath`）。这正是“开发密钥启动器被当成正式件”的风险来源。
- 产出 `<out>/荣盈魔方启动器.exe` 与 `<out>/launcher-build-receipt.json`。

### 5.3 回执字段

```text
receiptVersion, launcherVersion, commit, commitDirty,
embeddedKeysBase64[], embeddedKeyFingerprints[],
exeSha256, exeSize, outDir, builtAt(ISO),
toolchain{ go, node, pnpm, os }, trust: "self-declared"
```

- 不含 `signingKeyFingerprint`：**启动器构建不使用私钥**。
- `trust` 字段固定为 `self-declared`，提醒读者这是未签名声明。

### 5.4 组装器规则

组装器接收 `--receipt <path>`，并按下列规则处理：

**硬拒绝：**

- 回执缺失或不可解析；
- `exeSha256` 与传入 EXE 的实际 SHA-256 不一致（纯配错检测）；
- `embeddedKeyFingerprints` 与密钥台账中该启动器版本登记的钥匙集合不一致；
- `commitDirty` 为 `true`。

**仅警告：**

- `outDir` 与本次实际传入路径不一致（路径会变，且它本来就不是安全属性）；
- `builtAt` 陈旧或晚于当前时间（陈旧不是安全属性）。

### 5.5 回执的存放位置（边界）

回执是**构建侧与 QC 侧的产物**，**不得进入交付目录**。交付目录仍然只允许三样东西：盘根启动器、`荣盈魔方/` 程序目录、`使用说明.txt`（`scripts/lib/udisk-delivery.mjs` 的既有规则）。审计通过 `--receipt <path>` **从外部接收**回执，而不是在交付目录内寻找它。

### 5.6 交付审计加严

在 `scripts/udisk-delivery.mjs` 增加规则：

- `launcher-too-small`：现状只要求前两字节为 `MZ`（`scripts/assemble-udisk-delivery.mjs:60-67`），任何 ≥2 字节的 `MZ` 文件都能通过；
- `launcher-pe-invalid`：在 `MZ` 之外继续检查 `PE\0\0` 签名与机器类型；
- `launcher-key-mismatch`：在 EXE 字节中做**静态搜索**——预期公钥串必须出现，台账中其他已知公钥串必须不出现；
- `launcher-receipt-missing`：未提供 `--receipt` 时报错。为此审计工具新增 `--receipt <path>` 参数；**回执不位于交付目录内**（见 §5.5），审计只从该参数读取，不在交付目录里寻找回执。

同时修复现有缺陷：`scripts/lib/udisk-delivery.mjs:49-57` 的 `finding()` 把所有结果写死为 `error`，导致调用方的 `warn` 分支不可达。应让 `warn` 层真正可达。

**静态搜索的定位：** 它只是**廉价的配错检测**（sanity check），**不是**来源证明——EXE 可被重新打包，字节里出现某个公钥串并不等于它就是这个启动器。

### 5.7 运行时功能挑战（发布期 QC 证据）

静态检查不足以判断这个二进制究竟是哪一把，所以让启动器**自报身份并现场验签**：

1. 启动器报告**实际版本**与**嵌入公钥指纹**；
2. 对一个**由预期钥匙签名**的 manifest，验证**成功**；
3. 对一个**由未知钥匙签名**的 manifest，验证**失败**。

三条全部通过，才算“**这一把二进制在行为上符合预期**”。

⚠️ **这不等于来源可信。** 一个被篡改过的启动器同样可以伪造 `--describe-json` 的输出与验签结果。因此本节给出的是**防配错与来源核对材料**，属于发布期 QC 证据；真正的来源证明仍要等 Authenticode 或受信 attestation（见 §5.8）。

**新增两个 CLI，均不得触发更新：**

- `--describe-json`：向 stdout 输出 JSON（`{ schemaVersion, launcherVersion, embeddedKeys:[{fingerprint, base64}] }`）。**只走 stdout**，暂不引入 `--out`（依据见 §4.1 的实验结论）。
- `--verify-manifest <path>`：读取 manifest 文件，用内嵌公钥验签，输出结果 JSON（成功时含命中的 key 指纹），退出码仅在验签通过时为 0。

两个命令的**副作用约束（必须测试）**：不得读写更新事务状态文件、不得读写 `荣盈魔方-运行数据` 与 `荣盈魔方工作区`、不得启动任何子进程、不得访问网络、不得触发下载或交换。

**挑战样本的钥匙要求：自动化测试与生产发布质检必须分开。**

| 场景                               | 正向样本                                            | 负向样本                           | 生产私钥                                                  |
| ---------------------------------- | --------------------------------------------------- | ---------------------------------- | --------------------------------------------------------- |
| **仓库 / CI 自动化测试**           | 注入**临时 fixture 公钥**，用**对应的临时私钥**签名 | 用**另一把未知钥匙**签名，必须失败 | **不得出现**：不进仓库、不进测试夹具、不进 GitHub Actions |
| **生产发布质检**（启动器出厂核对） | 由**生产钥匙**签出的 manifest                       | 同上的临时未知钥匙                 | 不出现于工具链；样本在**已授权的离线签名会话**中产生      |

- 生产发布质检的正向样本优先直接使用**本次待发布的真实 manifest**；在没有待发布版本时（例如例行启动器质检），使用在已授权的离线签名会话中额外签出的**无害 manifest**。
- 无害 manifest 必须**按构造即不可应用**：使用客户端不会读取的 `channel`，或使用低于任何在役版本的 `version`。
- **生产发布质检的正向挑战绝不使用临时钥匙。**
- **临时生成的未知钥匙只用于必须失败的负向挑战**，且该钥匙绝不接触任何生产签名材料。
- 生产发布质检的结果属于**发布期 QC 证据**，按 §10 与发布记录归档，**不是**普通 CI 测试。

**消费者解析纪律：** `--describe-json` 的消费方校验 `schemaVersion` **精确相等**，遇到未知版本即拒绝。这是刻意的 fail-closed 选择：启动器比应用更新意味着发生了一次计划外的盘根替换，属于应停下调查的异常状态。

### 5.8 残留风险：没有 Authenticode

启动器本体**未做操作系统级代码签名**。后果：

- Windows SmartScreen 会拦截（“未知发布者”），普通用户可能点不过去；
- 无法借助操作系统机制验证启动器未被篡改；
- 这与本产品的 Ed25519 清单签名是**两件不同的事**：后者保护**更新内容**，前者保护**启动器本身**。

该残留风险必须写入密钥台账与发布记录，直到取得代码签名证书才可关闭。

## 6. 可恢复的人工 feed 上传器

### 6.1 三条不变式

- **I1** 客户端只读 `<channel>/manifest.json`；版本目录在 manifest 翻转前**对客户端不可见**。
- **I2** 版本目录**不可变**。
- **I3** manifest **只做原子替换**，且是流程的最后一步写操作。

### 6.2 参数与输入纪律

- `channel` 只接受 `internal` 或 `stable`，**白名单**，拒绝任意字符串。
- `version` 必须通过**严格 SemVer** 校验（与生成器 `assertVersion` 同口径）。
- **所有远端路径由两个固定根目录派生**，不接受任意远端路径参数：
  - **发布根** `<update-root>` = `/opt/rongying/updates`（公网可见，只放已发布的版本目录与频道 manifest）；
  - **状态根** `<state-root>` = `/opt/rongying/updates-state`（公网不可见，放 staging 与频道锁）。
    两个根都写死为常量，不由命令行传入；`--preflight` 负责核验它们与 §6.8 的文件系统前提。
- 上传器**只接收已经签名的 manifest**，**绝不读取私钥**。
- **在任何网络写入之前**，先完成**本地预验证**（即 §6.5 的第 1 步）：签名验证，以及 `channel`、`version`、`packageUrl`、哈希、大小的精确检查。任一项不过，**一个字节都不写**。

### 6.3 前置检查：`--dry-run` 与 `--preflight`

两者语义严格区分，不得混用：

| 模式          | 网络         | 检查内容                                                                                                                                                                                                                                            | 限制                                        |
| ------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `--dry-run`   | 完全离线     | 打印将执行的步骤、本地哈希与大小、目标路径、manifest 前后摘要                                                                                                                                                                                       | **不得宣称验证了权限、远端目录或 host key** |
| `--preflight` | **只读联网** | host key 是否匹配固定 known_hosts；远端目录是否存在、属主与权限位、有效账号、挂载点与设备号（**可写性指标**）；磁盘余量；锁是否空闲；目标版本目录是否已存在及其字节状态；**staging 目录与最终目录是否在同一文件系统**（比较 `stat -c %d` 的设备号） | 仍然**不写任何东西**                        |

**`--preflight` 的能力边界：** 只读检查能验证的是**可写性指标**——目录存在、属主、权限位、有效账号、挂载点与设备号（“同一文件系统”这个判据也由此得出）。**在没有真正写入之前，不得声称完成了端到端可写验证。** 真正的写入能力要到 commit 流程的 **stage（§6.5 第 2 步）** 才被证明。

### 6.4 SSH 信任固定

- `BatchMode=yes`，永不交互提示；
- `StrictHostKeyChecking=yes`，**永不自动接受新指纹**；
- 使用**仓库外**的固定 known_hosts；
- 台账**备案服务器 host-key 指纹**；指纹变化即停止并进入事故流程（可能是真的更换了机器，也可能是中间人）。

### 6.5 发布时序（固定，不得调换）

1. **本地预验证（任何网络写入之前）**：对三个产物完成签名验证，以及 `channel`、`version`、`packageUrl`、哈希与大小的精确检查。任一项不过即停止，记录 `fail`，**一个字节都不写**；
2. **stage ZIP + file manifest** 到确定性 staging 目录；
3. **远端复核**：核对 staging 内的字节（哈希与大小）确实与本地一致；
4. **获取频道锁**；
5. **锁内重新核验**：重新读取当前远端 manifest 的 SHA-256 作为 CAS 基线，并确认 staging 字节仍与 manifest 一致；
6. **原子提交版本目录**：`rename` staging → `<channel>/<version>/`；
7. **备份旧 manifest**（该频道首次发布时无旧 manifest，此时记录为“不存在”，不得跳过记录）；
8. **CAS**：再次读取远端 manifest 的 SHA-256，与步骤 5 记录的基线比较，不等则放弃并进入事故流程；
9. **写入临时 manifest**：文件名包含 runid，**与正式 manifest 位于同一目录**；
10. **原子翻转**：`mv -f` 替换正式 manifest；
11. **公网复验**：从公网重新拉取 manifest 与两个产物，独立复核签名、哈希、大小与 URL；
12. **审计**：写入本阶段记录，并以 `done`、`fail` 或 `incident` 收口（判定与锁处置见 §6.6）；
13. **释放锁**：**仅在 §6.6 判定为“可安全退出”时执行**；结果不确定时一律保留锁。

说明：第 1 步先于任何网络写入，是为了满足 §6.2 的输入纪律——本地预验证不过时连 staging 都不产生。步骤 6 在 manifest 相关步骤之前提交版本目录是安全的——由 I1 与 I2 保证它在翻转前对客户端不可见。若步骤 8 的 CAS 失败，已提交的版本目录与已做的备份都是无害的孤儿，**不自动清理**。

### 6.6 发布锁、owner 与陈旧锁恢复

- 锁为**原子 `mkdir`**（每频道一把）：`mkdir <state-root>/lock/<channel>`。创建失败即退出，**不等待、不强抢**。
- 锁内写 `owner.json`：`runid`、`operator`、`startedAt`、`planHash`（`channel + version + 三产物哈希`）、执行机标识。
- **陈旧锁不得自动破除。** 工具检测到锁存在时，只报告 owner 与时间，然后退出。
- 显式恢复：操作员执行 `--break-lock --reason "<文本>"`。工具必须：
  1. 打印原 owner 的完整信息并**要求操作员确认前一次运行确实不在进行中**；
  2. 在审计日志中记录破除动作、原 owner、原因与执行人；
  3. 然后才允许继续。
- 理由：自动破除陈旧锁会让两个并发运行同时通过，直接破坏 I3 与 CAS 的意义。

**锁的释放是有条件的，不是每次运行都释放。** 判定规则：

| 失败性质                            | 远端状态 | 收口状态   | 锁处置                        |
| ----------------------------------- | -------- | ---------- | ----------------------------- |
| 翻转（§6.5 第 10 步）**之前**失败   | 确定     | `fail`     | **释放锁**                    |
| 翻转**之后**失败                    | 不确定   | `incident` | **保留锁**（`lock-retained`） |
| **SSH 回执丢失**                    | 不确定   | `incident` | **保留锁**                    |
| 出现**第三种 manifest SHA**（§6.7） | 不确定   | `incident` | **保留锁**                    |
| 任何其他远端结果不确定的情形        | 不确定   | `incident` | **保留锁**                    |

- **保留锁时不得自动释放**，必须走本节的显式恢复流程（`--break-lock`），且该流程同样要求操作员确认前一次运行确实不在进行中。
- 理由：翻转之后的不确定性意味着远端状态可能已被改变而操作方并不知情；此时若释放锁，下一个运行会在没有人工确认的情况下继续操作同一个频道。

### 6.7 不确定结果处理

翻转后若无法确定结果，按**公网 manifest 的 SHA-256** 三分：

| 结果               | 判定                             | 动作                                                     |
| ------------------ | -------------------------------- | -------------------------------------------------------- |
| 等于**新** SHA     | 翻转已**完成**                   | 继续执行步骤 11 的完整复验                               |
| 等于**旧** SHA     | 翻转未生效                       | **允许重试**                                             |
| 等于**第三种** SHA | 有第三方并发修改，或发生未知情况 | **停止**，记录 `incident` 并保留锁（§6.6），进入事故流程 |

### 6.8 staging 目录的位置与续传

- staging 与锁目录位于**web 根之外**（例如 `<state-root>/staging/<channel>/<version>/`），避免 `/updates/.lock/...` 之类路径被公网读取而泄露操作员、runid 与时间。
- 该目录**必须与最终版本目录处于同一文件系统**，否则步骤 6 的 `rename` 不再是原子操作。这一点由 `--preflight` 用设备号比较**显式核验**，因为运维变更（例如把 `/opt` 改成独立挂载）会静默破坏该前提。
- **staging 标识绑定** `channel + version + 三产物哈希`。只有完全匹配才允许续传；不匹配时**不复用**，改放带 runid 后缀的独立目录交人工判断，**不自动删除**。
- 传输使用 **`sftp` 批量 `reput`（可续传）**，因为服务器**没有 `rsync`** 且 `scp` 不支持续传。

### 6.9 版本目录已存在时的处理（必须可恢复）

- 字节**完全一致** ⇒ **继续后续步骤**（让中断后可以恢复）；
- **任一字节不同** ⇒ **立即停止**；
- **不得简单拒绝**——那会让一次中断后的发布永远无法恢复。

### 6.10 `internal` → `stable` 的纪律

- `stable` **只能复用** `portable.zip` 与 `portable-files.json` 的**原字节**；禁止重新打包、重新压缩或修改时间戳；
- **`stable` manifest 必须单独离线签名**，使用 `channel: stable` 与 stable 的 `packageUrl`；
- **不得把 `internal` 的 manifest 改字段复用**：签名载荷包含 `channel` 与 `packageUrl`（`launcher/internal/update/verify.go:110-123`），改动即导致签名失效。

### 6.11 审计日志

- **从操作开始逐阶段追加**，**不是最后写一条**。阶段条目与 §6.5 的十二步一一对应，另加两条会话级条目：

  `open` → （执行过 `--preflight` 时追加 `preflight`）→ `pre-verify` → `stage` → `remote-verify` → `lock` → `re-verify` → `commit-version` → `backup-manifest` → `cas` → `temp-manifest` → `flip` → `public-verify` → `done|fail|incident` → （**仅可安全退出时**追加）`unlock`

  ⚠️ **`unlock` 不是每次都写。** 只有 §6.6 判定为可安全退出时才追加 `unlock`；不确定结果写 `incident` 并标记 `lock-retained`，**不写 `unlock`**。因此“最后一条是 `unlock`”才代表正常收尾；最后一条是 `incident` 就说明锁被有意保留、需要人工介入。

- 记录内容：runid、operator、时间、三个产物在**本地/远端/公网**的三段哈希与大小、旧 manifest 的原 SHA-256 与备份路径、新 manifest 的 SHA-256、每个阶段的结果码。
- 结果不确定时，日志必须能直接看出**卡在哪一阶段**。
- `--audit-out <path>` 为**必填**，且路径必须**位于仓库之外**，避免误提交。日志不自动提交。

### 6.12 权限边界

- 生产**应使用受限发布账号**：对版本目录可写、manifest 单独一步可换、不能改动其他内容。
- 现状：`/opt/rongying/updates` 与 `/opt/rongying/backups` 均为 `root:root 755`，**首次发布将临时使用 root**。
- **这是一处显式例外，必须记录残留风险**：root 一旦被脚本缺陷或误用影响，可以改动服务器上的任意文件；审计**只能事后发现，不能事前阻止**。
- 建立受限账号属于方案二范围内的加固。

### 6.13 nginx

- 新的 manifest 位于 `/updates/<channel>/manifest.json`，**不继承** `= /updates/latest.yml` 的 `no-cache`。
- 客户端使用 Electron 主进程的全局 `fetch`（undici，无隐式 HTTP 缓存），因此当前**风险低**。
- 建议追加 `location ~ ^/updates/(internal|stable)/manifest\.json$ { add_header Cache-Control "no-cache" always; }`，作为廉价保险，避免将来更换 HTTP 栈时出现陈旧 manifest。

### 6.14 中断语义汇总

| 中断位置                   | 后果                                         | 处置                                               |
| -------------------------- | -------------------------------------------- | -------------------------------------------------- |
| staging 传输中             | staging 不完整，客户端不可见                 | 重跑续传（staging 标识匹配时）                     |
| 步骤 2–5 之间              | 同上                                         | 同上；锁可能残留，按 §6.6 处理                     |
| 步骤 6 之后、步骤 10 之前  | 版本目录完整但无 manifest 引用，客户端不可见 | 重跑：字节一致则继续                               |
| 步骤 10 的 `mv` 中途       | 原子操作，不存在半截 manifest                | 按 §6.7 三种 SHA 判定                              |
| 步骤 10 之后、步骤 11 之前 | 状态未知                                     | 按 §6.7 判定；记录 `incident` 并**保留锁**（§6.6） |

### 6.15 回滚语义

§6.5 第 7 步备份的旧 manifest 是回滚材料。回滚动作 = 把频道 manifest **原子替换回备份**（同样使用含 runid 的临时名再 `mv -f`）。

⚠️ **回滚只能拦住“还没升级的”客户端，不能撤销已经发生的升级。** 原因是客户端有防降级判定：`manifest.version <= currentVersion` 时直接判为“已是最新”（`packages/desktop/src/main/ipc/update-handlers.ts` 所调用的 `packages/desktop/src/main/update/portable-manifest.ts:140`）。

由此有两条必须写清的结论：

1. **回滚的正确用途是“阻止继续扩散”**，不是“把用户退回去”。操作员不得把回滚当成降级手段。
2. **若确实需要让已升级的盘退回旧内容**，只能发布一个**版本号更高、内容回退**的新版本（版本号必须递增才可能被客户端接受），并且必须另开事故流程，不得在本发布流程内顺手做。

回滚同样受 §6.5 时序与 §6.6 锁的约束：**不得绕过频道锁直接改 manifest**，回滚也必须写审计记录（执行人、理由、被回滚到的 manifest SHA-256）。

### 6.16 关于“ASCII 临时名”这条历史纪律

旧的操作记录要求“先传 ASCII 临时名、再改名”。其原因是**中文安装包名**经 `scp` 传输会被破坏。新 feed 的文件名已经是纯 ASCII（`portable.zip`、`portable-files.json`、语义化版本目录），因此**“改名”这一步在这里没有存在理由**。

保留“临时名 → rename”是**另一个**理由：原子性与可见性控制，而 I1 与 I2 已经保证客户端看不到半成品。**不得把旧仪式照抄过来并声称它是安全要求。**

## 7. CI 边界纠偏

- **保留** PR 侧的 Go 测试与 Windows 真 PE 检查（`.github/workflows/pr-check.yml` 的 `portable-update-windows`）。
- **完全解耦**：`portable-update-release` 当前依赖 `needs: [prepare-release, release]`（`.github/workflows/release.yml:186-187`），而 `release` 是上游多平台（macOS/Linux/Windows）发布流水线。应拆成**独立 workflow**。
- ⚠️ **拆成独立 workflow 后不能跨 workflow 使用 `needs`**，因此必须把**版本准备逻辑一并迁入**（tag 格式校验与 `packages/desktop/package.json` 版本一致性检查，现位于 `release.yml:32-52`）。
- **生产私钥禁止进入 GitHub secret ⇒ CI 不得产出生产签名 manifest。** CI 只能二选一：
  - **A.** 使用**临时测试钥**生成**明确不可发布**的测试制品（名称或 label 中带 `test-only`，使用测试频道或不指向 feed）；
  - **B.** 产出 **unsigned 的 ZIP 与文件清单**，生产 manifest 由**离线流程**签名。
  - **推荐以 B 为主、A 为辅**：B 保留 CI 的“能否构建、能否过门禁”价值，同时把签名能力留在离线侧。
- **删除未被消费的假门禁** `MOFANG_UPDATE_FEED_UPLOAD_TOKEN`（`release.yml:203, 206`）以及计划书中的对应条目。删除**必须同时**修改 `scripts/lib/portable-update-ci.test.mjs:38`（其断言正是“workflow 中存在该字符串”）；该测试会因此变红，这正说明护栏有效。
- **不得把“替换 5 处 `clawwork-ai/clawwork`”当作完成**：`release.yml:182, 312, 397, 404, 413` 与 `.github/workflows/update-homebrew.yml:21` 背后是上游整套发布语义（Apple 证书、AppImage/deb、Homebrew tap，以及 `--publish always` 搭配 `provider: generic`——后者本身矛盾，generic provider 不支持上传）。简单替换会让这些 job**看起来能跑、语义是错的**。正确做法是**显式删除或停用**对本产品无意义的 job 与 secret 引用。

## 9. 方案一与方案二的关系

### 9.1 方案一（本设计）

单一离线生产钥匙 + 真实启动器版本双重门禁 + 可恢复人工上传器。

- 能得到：能做对、能恢复、能审计，且不夸大能力。
- 明确**不接受**的能力：无密钥撤销、无安全轮换、无操作系统级代码签名。
- 时间敏感性：§4 的三个缺陷与 §5.7 的 `--describe-json` / `--verify-manifest` 必须在**第一把启动器出厂之前**落地。目前一把都未出厂，因此现在改是免费的；一旦出厂，任何信任模型层面的变更都意味着全量更换 U 盘。

### 9.2 方案二（长期，单独立项）

离线根授权 + 可撤销且防回滚的信任策略：离线根钥匙签发**信任策略**（含 epoch、单调计数器、吊销列表），启动器内嵌**根公钥**而非叶子公钥；策略更新与 manifest 分离，从而能够表达“某把钥匙作废”与“不接受低于 epoch N 的 manifest”。

必须先做**独立威胁建模**：撤销的时效、离线根的使用频次、策略自身的防回滚、策略签名的分发方式。

之所以必须单独立项：

1. 它要改动启动器的信任模型与 manifest 结构，而 §1.2 第 3 条的**严格解码**意味着任何结构变化都要求**整体替换启动器**；
2. epoch 与防回滚状态需要在盘上持久化，并跨盘符变化存活；
3. 它不是“顺手加个字段”。

### 9.3 两者的确切关系（无并存）

- 方案二**改变启动器的信任模型**。因此，**按方案一构建的启动器必须被人工替换**，否则无法进入方案二的信任模型。
- **不存在混合机群或并存**：由于严格解码，方案一的启动器连方案二的 manifest 都无法解析。
- **可以复用的是基础设施，不是信任模型**：上传器、审计链、离线签名纪律、构建回执与 QC 工具、runbook 的操作结构与故障处理表格，都可以原样保留。**信任模型本身必须整体替换。**
- 方案二不是方案一的替代品，而是它的后继；方案一交付的这些基础设施是方案二的前置件。

## 10. 测试与证据要求

本设计的每一项行为改动都按既有纪律执行：**先红后绿 → 变异验证 → 完整门禁 → 显式 pathspec 独立提交**（禁止 `git add -A`）。

必须覆盖的行为（每项都要有对应的红灯证据）：

1. 应用读取真实启动器版本；启动器缺失、超时、非零退出、输出非严格 SemVer 时**一律拒绝更新**；
2. `LAUNCHER_PROTOCOL_VERSION` 删除后不再有任何“假装是启动器版本”的常量；
3. 启动器在交换前用真实编译版本校验 `minLauncherVersion`；
4. `--describe-json` 与 `--verify-manifest` 的**副作用约束**：不触碰事务状态、不触碰运行数据与工作区、不启动子进程、不访问网络；
5. **自动化测试的挑战样本**：仓库与 CI 只能注入临时 fixture 公钥——正向样本用**对应的临时私钥**签名，负向样本用**另一把未知钥匙**签名并必须失败；生产私钥**绝不**进入仓库、测试夹具或 GitHub Actions；
6. **生产发布质检的挑战样本**：由生产钥匙签出的无害或真实 manifest，在获授权的离线签名会话中产生；这是**发布期 QC 证据**，按发布记录归档，不是普通 CI 测试；
7. 回执的四条硬拒绝规则各自可被单独触发；
8. `outDir` 不符与 `builtAt` 陈旧**只警告不拒绝**；
9. 上传器的固定时序不可调换：**本地预验证必须先于任何网络写入**；跳过锁、跳过 CAS、提前翻转 manifest 都必须被拒绝；
10. 锁为原子获取；陈旧锁**不自动破除**；`--break-lock` 要求确认并留痕；**翻转后失败、SSH 回执丢失、出现第三种 SHA 或任何远端结果不确定，都必须保留锁**；
11. §6.7 三种 SHA 结果分别走三条不同分支，且第三种分支保留锁并记 `incident`；
12. §6.9 版本目录字节一致时可恢复、不一致时停止；
13. `--preflight` 检测 staging 与最终目录是否同一文件系统；且**只声明可写性指标**，不得声称已完成端到端可写验证。

**记账纪律：** 任何未执行或被跳过的检查一律记为“未验证”，不得计入通过。

## 11. 未决事项（需用户决定）

1. **生产密钥的生成时机与执行者**：本设计未获授权生成任何密钥。需要明确何时、由谁在离线环境生成，以及公钥与指纹何时进入台账。
2. **本轮是否同时落地启动器 CLI 扩展**：`--describe-json` 与 `--verify-manifest` 现在做是免费的（尚无启动器出厂）。若推迟，则 §5.7 的运行时挑战无法执行，来源核对会停留在静态检查。
3. **本轮是否落地上传器脚本**：可选择只写 runbook、由人工执行，或同时实现 `scripts/feed-publish.mjs`。二者都满足“不编造上传命令”的要求，但只有后者能自动保证 §6.5 的时序。
4. **受限发布账号是否本轮建立**：当前方案接受“首次临时使用 root”这一显式例外。若不接受，则需要先做服务器目录属主与账号改造。
5. **Authenticode 证书是否采购**：§5.8 的残留风险只有在取得代码签名后才会关闭。
6. **发行渠道的 host-key 指纹备案由谁核对**：本设计要求备案服务器 host-key 指纹，但未指定由谁在何时完成首次核对。
