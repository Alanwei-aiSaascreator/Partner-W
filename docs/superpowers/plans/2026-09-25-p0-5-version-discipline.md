# P0-5：版本纪律 与 便携更新的"两次明确动作"回归

**这份不是功能**，是把两件**容易被顺手破坏**的事写死在纸上：版本号怎么给、
以及便携更新那条链**必须保持两次明确动作**。

---

## 一、版本纪律（0.0.33 / 0.0.34）

| 版本       | 是什么                                        | 关键约束                                                          |
| ---------- | --------------------------------------------- | ----------------------------------------------------------------- |
| **0.0.33** | **手工基础包**（客户端三修 + 新启动器一起换） | `minLauncherVersion` **从这一版起写 `0.0.28`**（不得再写 0.0.27） |
| **0.0.34** | **第一个从普通用户 UI 触发远程更新的版本**    | 它才是"盘上自己升上去"那条链的首次真实验收                        |

⚠️ **为什么必须手工换一次基础包**：便携更新**从不替换启动器**（信任根），
而盘上那些启动器（0.0.27 及更早）**点「重启并更新」必失败**（换目录竞态，两条根因缺一不可）。
⇒ **启动器侧的修复到不了任何现有盘**，只能靠换基础包。

⚠️ **同版本不算更新**：`portable-manifest` 判 `<= 0` 就是"已是最新"。
⇒ 要给盘上已经更到 0.0.32 的机器带东西，**必须升号**。

## 二、⛔ 授权边界（本轮**没有**、也不许有）

- **未经单独的"打包"授权** ⇒ 不 `build:win`、不出包。
- **未经单独的"发布 internal"授权** ⇒ `feed-publish.mjs` 的三道门（dry-run / preflight / commit）一道都不开。
- **stable 一律另行请求** ⇒ 不碰 `stable`、不碰 `latest.yml`、不重签正式 manifest。
- 本轮所有产出**只存在于 git 里**（两个工作树的分支上），**没有**任何 build / sign / upload / manifest 变更。

## 三、"两次明确动作"回归（C0，已实跑）

**判据**：便携更新那条路是**两次明确动作**，不是一键，也**不许**被合并成一键：

1. 点「**下载并准备更新**」⇒ **只**下载、校验、解压、逐文件核对（`downloadUpdate`）；
   ⛔ 这一步**绝不**调 `installUpdate`。
2. 只有到了 `ready`，才出现「**立即重启并更新**」⇒ 才 `installUpdate`。

**回归读数**（2026-09-25 实跑，C 分支 `a1f7b08a`）：
`test/portable-update-about.test.tsx` + `test/update-status.test.ts` = **36 条全绿**。

被测试**按名**钉住的四条（这些名字就是判据，删掉任何一条都会红）：

| 测试名                                                           | 它守的是什么           |
| ---------------------------------------------------------------- | ---------------------- |
| `② 点入口只调 downloadUpdate —— 这时绝不调 installUpdate`        | **第一次动作不许越界** |
| `⭐ 只有 ready 才出现「立即重启更新」`                           | 第二次动作的**前提**   |
| `④ 失败绝不安装：错误相位下没有重启钮，installUpdate 一次都没调` | **失败路径**           |
| `③ 顺序：点完之后是**准备中**（没有重启钮），ready 到了才有`     | 两次动作的**顺序**     |

⚠️ **两次动作不是缺陷**（用户 2026-09-25 明确拍过）：本轮验收就按**两次明确用户动作**算通过，
不要为了"一键"去打断验收。
