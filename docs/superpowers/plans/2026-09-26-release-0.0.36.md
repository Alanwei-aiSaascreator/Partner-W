## 一、先探针，后设计（盘 E: 0.0.35 + 真模型，同机同模型同提示词对打）

### 1.1 被否掉的旋钮

配置层那个看起来最像的 `tools.elevated` **结构性无效**：运行时源码里它要
`Boolean(channel)`，而 `channel` 是 Telegram / Discord 那种**外部渠道**（`sandbox-cli-*.mjs:181`），
桌面端恒为 `(unknown)` ⇒ `allowedByConfig` 永远是 false。保留在红线里不动，也不参与本设计。

### 1.2 真正的旋钮：会话权限模式

`session-permission-exec-mode-*.mjs`：

```js
const workspaceOnly = policy.mode !== 'full'; // ← 一行决定"能不能碰工作区外面"
```

| 档位        | workspaceOnly | exec     | bypassHostApprovalFloors |
| ----------- | ------------- | -------- | ------------------------ |
| `read-only` | true          | deny     | false                    |
| `guarded`   | true          | ask      | false                    |
| `workspace` | true          | auto     | false                    |
| **`full`**  | **false**     | **full** | **true**                 |

合成规则（`agent-tools-*.mjs:375`）：**会话模式压过配置** ——
`sessionCoreToolPolicy?.workspaceOnly ?? fsConfig.workspaceOnly === true`。

### 1.3 治理：网关自己给「全权」加了 admin 门

`method-scopes-*.mjs`：`sessions.patch{permissionMode:'full'}` 与 `sessions.create{...full}`
都要 **`operator.admin`**；其它档位只要 `operator.write`。我们握手时**已经在申请**这个 scope
（`ws/gateway-client.ts:483`），且 `ws:session-patch` 是整包透传（`ws-handlers.ts:653`）
⇒ **不需要新管道、不需要动主进程**。

### 1.4 行为读数

| 判据                           | `full`                        | 默认（无模式 + 配置 `workspaceOnly:true`）                                 |
| ------------------------------ | ----------------------------- | -------------------------------------------------------------------------- |
| 读 `C:\Windows\win.ini` 第一行 | ✅ `; for 16-bit app support` | ❌ `Path escapes sandbox root (~\...\workspace): C:\Windows\win.ini`       |
| `exec: cmd /c echo PROBE_OK`   | ✅ `PROBE_OK`                 | ❌ `exec denied: Headless runs cannot wait for interactive exec approval.` |

⭐ 第二行那条报错**正是用户早先贴给我的原话** ⇒ 全权档**顺手修掉了那条"headless 等不了审批"**。
⭐ **负对照**：`patch {permissionMode:'yolo'}` 被 schema 当场拒
（`must be equal to constant; must match a schema in anyOf; must be null`）
⇒ 上面的"成功"不是字段被静默忽略。
⭐ 探针期间配置**按备份还原**（当前仍是四条红线），而 full 会话照样读到了 `C:\Windows\win.ini`
⇒ 「会话模式压过配置」这条代码读法**被真机证实**。

## 三、🔴 两条读数互相矛盾：0.0.35 账本说「pnpm check RC=0」，但红灯当时就在

跑这一版的门禁时连续撞到两条，**都是 0.0.35 自己的提交引进的、且都在当时的 HEAD 里**：

1. **`check:ui-contract`** —— `FilePreview.tsx` 的 `bg-white`，由 0.0.35 的 HTML 预览
   `4cfaded4` 引入。⚠️ 门禁的 allowlist 对**调色板色**这一类**结构上不适用**
   （`check-ui-contract.mjs:117` 只对 `layout-escape` 生效）⇒ 只能换语义 token。
   加 `--document-canvas`（**两个主题里都是白的，故意的**：网页按白纸写）。
2. **`typecheck:tests`** —— `docgen-pdf.test.ts:138` 的 TS2493，由 0.0.35 的 PDF
   `6f0c9236` 引入。正是仓库**自己的注释里写过**的坑：桩不写参数类型，`mock.calls`
   就是长度 0 的元组。

⇒ **结论**：0.0.35 账本里那条「`pnpm check` RC=0」**不可能是发布那一刻的读数**
（两条都确定性失败，且都源自那一版自己的提交）。可能是在更早的提交上读的，
或者那次跑根本没跑到这两步。**已按"发出的包带着红门禁"这件事本身修掉**，
并把这条教训留档：**"门禁 RC=0"必须绑在"哪个尖端"上，否则它是一句没有主语的话。**

## 四、⭐ 顺手抓到的 i18n 漂移（i18n 门禁查不出这一种）

`fileBrowser.workspaceAccessDescription` 的 **en / ja / ko / de / es / fr / pt 七份**
写的根本不是中文那句承诺（是「Assistants view this workspace…」那类），
只有 zh / zh-TW 是「只使用当前任务和你添加的文件…」。

⇒ 也就是说：**这句承诺在七个语言里从来没被说出口过**。
i18n 门禁只查「key 在不在、有没有没用到的」，**查不了"九份说的是不是同一件事"**。
（已顺手统一。要不要给门禁加一条"语义漂移"检查，是 0.0.37 的事。）

## 六、这一轮的设计取舍（写下来，免得下次又讨论一遍）

1. **默认档不下发任何东西**（而不是下发 `guarded`）⇒ "没开开关"与 0.0.35 行为**逐字节相同**。
2. **红线一个字不动**：走会话模式（运行时里它按设计压过配置），**不去改**
   `state-config.ts` 的 `workspaceOnly` / `exec.mode` / `deny`。
3. **打开要过同意门，关掉不设门** —— 收回权限再要一次同意是敌意设计。
4. **先切会话、成功了才落设置** ⇒ 切失败时界面**不会**显示"已开"。
5. **徽章只在全权时显示**（spec 原写"常显"，实现时收窄；spec 已同步更正并写明理由）。

## 七、这一轮**没做**的（欠账，0.0.37 开头）

1. **打包态真机验收**：见下节，这是**唯一**没拿到的那条读数。
2. 0.0.35 欠的三件（`cache:'no-store'` / 老盘拿不到新技能 / 身份中心客群卡打通 + `.html` 类型标签）。
3. 「已存在的其它任务」那一档**只在有当前任务时**才被开关改到；没有任务时开关只落设置
   （文案已如实说"下次新建任务时生效"）。要不要给"批量改历史任务"一条路，待拍。
4. i18n 语义漂移检查（见 §4）。

## 八、⚠️ 这一版**没验到**的（如实）

- **打包态（built package）真机验收**：没做。原因：dev 实例过不了登录门
  （`authState === 'required'` ⇒ 登录页，而 dev 没有激活态），而把未定版的构建铺到盘 E:
  会动到用户正在准备给领导的那张盘。**行为核心已经在真机上验过**（§1.4 两条 + 负对照），
  逻辑面由单测/组件测/接线集成测三层 + 全仓门禁覆盖；
  **唯独"装配进包之后仍然如此"这一条，要等下一版发布时补**。
- 徽章在真机上"看起来对不对"（颜色/位置）：只有组件测与门禁，没有肉眼读数。
