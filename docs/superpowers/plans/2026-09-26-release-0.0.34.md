## 二、这一轮量出来的硬事实

### 1. ⛔ 团队助手的**中文名建不出来**（新发现，从**出货包**里证实）

**结论**：给 `agents.create` 传一个**纯中文**的名字，**建不出来** —— 网关回 `invalid-name`。

**证据链三处，最后一处是出货产物本身**：

1. 出货运行时里那一份 `dist/agent-id-GA8mwdTG.mjs`（**本机已部署的那份**，
   `%APPDATA%\@clawwork\desktop\runtime\deployed\2026.9.3-win32-x64-58ed077d9f52\node_modules\openclaw\`）：

   ```js
   const VALID_ID_RE = /^[a-z0-9][a-z0-9_-]{0,63}$/i;
   const INVALID_CHARS_RE = /[^a-z0-9_-]+/g;
   function normalizeAgentIdStrict(value) {
     const trimmed = (value ?? '').trim();
     const normalized = normalizeLowercaseStringOrEmpty(trimmed);
     if (VALID_ID_RE.test(trimmed)) return ok(normalized);
     const agentId = normalized
       .replace(INVALID_CHARS_RE, '-')
       .replace(LEADING_DASH_RE, '')
       .replace(TRAILING_DASH_RE, '')
       .slice(0, 64);
     return agentId ? ok(agentId) : err('unrepresentable');
   }
   ```

   ⇒ `荣盈办公助手` 的每个字符都在 `[^a-z0-9_-]` 里 ⇒ 全被替成 `-` ⇒ 再去掉首尾 `-` ⇒ **空串**
   ⇒ `err("unrepresentable")`。**没有音译、没有哈希、没有随机后缀。**

2. 同一个出货包里的 `dist/agent-create-BSK3Nvv3.mjs`：

   ```js
   function validateAgentIdInput(rawId, options = {}) {
     const displayName = options.displayName ?? rawId;
     const normalized = normalizeAgentIdStrict(rawId);
     if (!normalized.ok) return { ok: false, reason: "invalid-name",
       message: `Agent name "${displayName}" has no valid id characters. Use at least one letter a-z or digit.` };
   ```

3. 客户端确实把**原始名字**送过去了：`packages/core/src/services/team-installer.ts:147`
   `deps.createAgent({ name: agent.name, workspace })`，而 `agent.name` 来自
   `TeamsPanel/useTeamInstall.ts:89-93` 的 `a.name.trim()` —— **没走 `toSlug`**
   （`toSlug` 算出来的 slug 只当本地进度键用）。

**影响面**（不是全坏，但有一条真坏的）：

- 预置的 6 个助手**不受影响**：它们先用 ASCII 名建、再用 `agents.update` 改成中文名
  （`preset-agent-installer.ts:164-170`）。盘上的 `rongying-office` / `高效办公` 就是这么来的。
- **AI 建队**这条路**在提示词里已经写了硬要求**（`TeamBuilderDialog/index.tsx:67`：
  "Team name and all agent names MUST be in English (ASCII only)"）——
  所以常见路径多半没事，**但那是提示词约束，不是代码约束**：模型不听话、
  或者用户手动把成员名改成中文，那个成员就会**静默降级**成一条警告
  （`team-installer.ts:148-157`），用户看到的是「Failed to create agent "…"」。

**为什么这一版不改**：修法要动 `packages/core` 的建队契约（照预置那条路
"先用可建的名字建、再改名"），而且 `deps` 里今天没有 `updateAgent`。
**发布前 30 分钟改建队主路径不是个好交易** —— 记成 0.0.35 的第一件事。
⚠️ 它**不是**"跨机器丢注册"那条，两条是**不同的**毛病（见下）。

### 2. 团队"跨机器不工作"的真正形状（回答用户点的那条）

**不是"文件没跟盘走"，是"注册表在机器上"。**

| 东西                                     | 在哪                                                                        | 跟盘走吗                                   |
| ---------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------ |
| agent 的**注册**（id + 名字 + 绝对路径） | `<state-dir>/openclaw.json` 的 `agents.entries`                             | ❌ **机器本地**                            |
| 每个 agent 的库与会话                    | `<state-dir>/agents/<id>/{agent,sessions}/`                                 | ❌ 机器本地                                |
| 机器本地的 id→库路径索引                 | `<state-dir>/state/openclaw.sqlite`（`agent_databases` 等，**存绝对路径**） | ❌ 机器本地                                |
| agent 的**身份文件**                     | `<workspace>/rongying-agents/<id>/{AGENTS,IDENTITY,SOUL,USER}.md`           | ✅ 在盘上                                  |
| 客户的**团队名册**                       | `<workspace>/.clawwork.db` 的 `teams` / `team_agents`                       | ✅ 在盘上，**但只有 `agent_id`、没有名字** |
| 便携态的 state 目录                      | `<usb-user-data>/state/<sha256(token)[:24]>`                                | ✅ 但**每块盘一个独立注册表**              |

⇒ 换机器插盘时，**盘上有身份文件、也有团队名册，唯独机器上没有那个注册**
⇒ 团队指向的 `agent_id` 在本机不存在。**名字要靠注册表才有**（`agents.entries.<id>.name`），
所以"盘上有花名册但没名字"这个现象是这么来的 —— 与早先的判断一致
（`agent-registry-lives-on-the-machine-not-the-disk`）。

**这一版仍然不改**：正确修法是"插盘时按盘上的花名册把注册补回去"，
而那需要先决定**从哪份真相重建**（身份文件？名册？两者冲突怎么办）——
是个产品决定，不是我自己能拍的。

### 3. 8 秒超时：根因仍未坐实，但从今天起**复发会留下能分辨的证据**

原有的日志只有 `[commercial] <label> timed out after 8000ms` —— 说的是**我们不等了**，
没说那条请求本身怎么了。而分根因只需这一条读数：

| 放弃之后               | 说明            | 该往哪修                   |
| ---------------------- | --------------- | -------------------------- |
| 几秒后**成功**返回     | 后端/网络就是慢 | 调超时、加退避             |
| 直到被中止都**没回来** | 卡住/排在锁后面 | 查会话刷新锁、查主进程停摆 |

`aea5ff34` 之后，超时那一刻会**继续看着同一个 promise**，落定时记一行
`[commercial] <label> we gave up, then: settled|aborted|failed at <ms>ms`。
⚠️ **只观测，不改行为**：不重试、不改超时、不碰返回值。
⚠️ 那一行**只有标签、耗时、结论**：错误原文（实机里带完整私有 URL、手机号、验证码）
**结构上到不了写日志的地方**——不是靠"记得别写"，是那个对象压根没传进去。

### 4. ⭐ 应用内预览 PDF：**证实能渲染**（这一条本该早做）

**为什么必须真跑**：`webPreferences` 里**没有** `plugins: true`
（`src/main/index.ts:161-166` 只有 `sandbox` / `contextIsolation` / `nodeIntegration`），
而"Chromium 自带的 PDF 阅读器在这个版本、这组开关下**到底能不能内嵌渲染**"
**凭记忆答不准**。渲染不了时 Chromium 会把它当**下载** ⇒ 判据很硬：
`will-download` 一响就等于没渲染。

**两次探针的读数**：

| 测的路径                                       | 结果                                                                             |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| `<iframe src="file:///…pdf">`                  | 截图里是**完整的阅读器**（工具栏、缩略图栏、"Hello PDF"），`downloads=0`         |
| **`<iframe src={blob:}>`（App 真正走的那条）** | 同上，`downloads=0`，`nonWhiteRatio` 0.6972 vs 前一条 0.6976 —— 两次渲染结果一致 |

⚠️ 第二条才是要紧的那条：App 里是
`URL.createObjectURL(new Blob([bytes], { type: 'application/pdf' }))`，
**和 `file://` 不是同一个东西**（Chromium 认 PDF 的判据里有 URL 形状这一项）。

**顺带查到**：预览源有 40 MiB 上限（`artifact-handlers.ts:34` 的
`MAX_PREVIEW_SOURCE_BYTES`，作为 `maxBytes` 传给读取）⇒ 超大文件不会把主进程拖垮。

⚠️ 手法记录：探针 v1 **一次读数都没留下**（Electron 起来后没走到写文件那一步，
看起来像"跑过了、没问题"）。v2 重写成"**每一步先写文件再做事**"，
才拿到上面这两行。**探针没有读数 ≠ 结论是好的。**

### 5. ⭐ 构建门禁当场拦住了一次**我自己的**错误

第一次构建 **失败**，因为我把 `MOFANG_UPDATE_PUBLIC_KEY_B64` 填成了
`D:/mofang-update-keys/mofang-update-public-key.txt` 的**整个文件内容**——
那份文件是**记录文件**（`keyId:` / `publicKeyBase64:` / `fingerprint:` / `createdAt:` 四行），
不是裸 base64。

门禁（`scripts/require-update-public-key.cjs --require-env`）**拒绝出包**并说清了后果：
"内嵌的会是空串 ⇒ 盘上'检查更新'永远失败，而**报的是 signature-invalid**，
用户看到的是一句对不上的话"。**它没有静默打出一个没有钥匙的安装包。**

正确取值（三个来源互相印证，**没有只用记录文件**）：

| 来源                                                        | 值                                                             |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| 记录文件 `publicKeyBase64:`                                 | `MCowBQYDK2VwAyEACBeiQuFzi8RoEWwaqRiEgC9jiPVX5kvtf8ai8kt2wQA=` |
| **出货启动器** `荣盈魔方启动器.exe`（Go，直接 grep 二进制） | 同上                                                           |
| 客户端 `resources/app.asar`                                 | 同上                                                           |

⚠️ 手法记录：第一次用 `strings ... | grep` **什么都没找到**，差点得出"启动器里没嵌钥匙"的错结论
—— `strings` 的切分方式会把它拆散。换成对二进制直接 `grep -a -o` 就出来了。
**探针没找到 ≠ 东西不在**，这一条本仓已经栽过很多次。
