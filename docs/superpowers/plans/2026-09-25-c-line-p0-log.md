### C1 这一刀的判据（用户原话的形状）

用户骂"卡住"多半不是因为真的卡住，而是**看不出它是否还在动** —— 2026-09-25 真日志：
六分钟里那块面板**一个字都没变**，一句不动的话配一条脉冲的条，等待与假死在观感上没有区别。

- 格式复用聊天活动条已有的 `formatElapsed`（`12.4s`）—— **不新造第二套格式**。
- ⚠️ **只在"还在准备"时报时**：已经有结论（失败 / 就绪）时秒数只是噪音，
  而且会暗示"再等等也许就好了"—— 那正是这一整轮要消灭的形状。
- ⚠️ 它量的是**这块面板从出现到现在**，不是"从进程启动"：渲染层拿不到更早的时间戳，
  把它说成从开机算起就是编。两者相差通常只有几秒。

**证据**：变异 4 杀 + 1 对照全过；`typecheck` / `typecheck:tests` / `lint` / `format:check` /
`check:i18n` / `check:renderer-copy` / `check:ui-contract` 全 RC=0；相关 3 个测试文件 57 条全绿。
⭐ 其中两条变异证明两个否定用例**互相独立**（去掉 hasError 判断只杀"失败后不报"，
去掉 conversationReady 判断只杀"就绪后不报"）—— 不是一条测试的两种写法。

⛔ **真机未验**。

## ⛔ 卡住的两件，以及它们为什么卡

**C2 的"网关失败显示明确原因"** 与 **C3 的"团队 agent 卡片/对话入口"** 都**结构上**
依赖 B 线的产出：

| 要显示的                                               | 数据在哪                                           | 现状                                                |
| ------------------------------------------------------ | -------------------------------------------------- | --------------------------------------------------- |
| "18789 被别的程序占用" / "网关不认我们" / "等就绪超时" | B 线的 `deriveStartupReadiness().ai.failureReason` | C 分支**没有**（B 在 `af52cd70` / `b05cdd19` 才加） |
| 团队 agent 缺运行时 ⇒ "需要安装"                       | B 线的运行时/目录状态                              | 同上                                                |

**授权那一半已经达标**：`relayFailureText` 覆盖 4 类确定失败
（未激活 / 卡属于别的组织 / 卡失效 / 名额已满），每类都带出路，不是一句笼统的"出错了"。
`ai.phase === 'error'` 在 C 分支上只有"目录里确实没有中转模型"一种成因，文案是"暂时没有可用模型"。
**想再进一步就只能猜**（是没激活？是额度？是网关？）—— 没有证据的出路比没有出路更坏，所以不做。

### 为什么**不**直接把 B 合进 C

章程写的是「**B / C 互不合并**；将来由**发布线**吸收」，用户也说了要
「**最终另建干净 integration worktree**」。C 现在 merge B 会让那个 worktree 失去意义，
而且会让两条线的改动在各自分支上互相出现 —— 正是章程要防的事。

⇒ **这两件登记为 integration worktree 的第一批任务**（见下）。信息不会丢，
只是不在 C 分支上做。
