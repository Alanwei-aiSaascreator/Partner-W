## 二、上半场：身份中心为什么"点击没反应"（真机复现的结论）

用户原话：「身份中心里面改不了，重新选择、换标签这些点击没反应」。

**真机复现**（盘上 0.0.34，CDP 真实鼠标事件 + `elementFromPoint`）：

| 控件                                          | 读数                                        | 判定          |
| --------------------------------------------- | ------------------------------------------- | ------------- |
| 五个标签 / 重新选择 / 换一个标签 / 应用此画像 | **全都真的执行**，`topAtPoint` 就是按钮自己 | ✅ 好的       |
| 「其它客群」四张卡                            | `cursor:auto`、无 onClick、`tagName=DIV`    | ❌ **死的**   |
| 「推荐技能」7 个                              | 文案在网关里不存在                          | ❌ **假的**   |
| 画像正文                                      | 常量，与选择无关                            | ❌ 点了不会变 |

⇒ **不是事件坏了，是页面是个空壳**：能点的都点了，什么都没发生。
**修复**：客群卡换成 7 个真实助手（`resolveAssistantWorkspace`）、画像随（客群+标签）实时变、
推荐技能换成该助手**真实的四件事**、保存**合并写进每个助手的 `USER.md`**（读→合并→写，
绝不覆盖用户已有记忆，超 4000 字如实拒绝）。

⚠️ 教训：v1 有 16 条测试全绿，它们问的是"按钮有没有 handler"。
**jsdom 测得到 handler，测不到"点了以后世界有没有变化"** —— v2 的断言改成"点下去看得见什么"。

## 五、这一轮抓到的两个真问题（都留了证据，未修）

### 1. 🔴 同一个进程里重复「检查更新」会读到**缓存里的旧清单**

- **证据**：点检查更新时**服务器访问日志里零请求**（日志实时，同一分钟有别的流量）；重启进程后同一步立刻
  得到 `0.0.35 / available`。
- **方向**：清单响应只有 `ETag`/`Last-Modified`、**没有 `Cache-Control`**，而主进程的 `fetch` 走 Chromium 缓存
  ⇒ 启发式新鲜度把旧清单继续当新鲜用。
- **修法（一行）**：抓清单时 `fetch(url, { cache: 'no-store' })`。
- **影响**：发布新版本后，**一直开着的**应用可能一直说"已是最新"（重启即可看到）。与"切频道要重启"同族。

### 2. 🔴 便携盘上切「更新通道」必须重启进程（上一轮已在记忆里留档）

通道在更新服务初始化那一刻被读走并锁进闭包 ⇒ 同进程里改设置不重建服务。**两件事合起来是同一课**：
**"设置改了就立刻生效"和"检查更新会真的去问服务器"这两个假设，都必须有测试钉住。**
