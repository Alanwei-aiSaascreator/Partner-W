## 🔴 真机验收抓到的更新链缺陷（0.0.28 与 0.0.29 这段代码**逐字相同**，两个版本都有）

**症状**：点下载 ⇒ `{ok:false, error:'unknown'}`、相位 `error`，**连 `portable.zip` 都不去取**。

**定位过程**（记下来，下次别重走）：盘上日志里 `updater` 域**一条都没有** ⇒ 只能挂
**主进程 Node inspector**（`--inspect`）才捞得出来：`Debugger.setPauseOnExceptions({state:'all'})`
抓到

```
Error: ENOENT: no such file or directory, statfs
       'E:\.荣盈魔方更新\download\<事务 id>'
```

**根因**：`downloadPortablePackage` 直接用 `fs.statfs` 量 `dirname(destinationPart)` ——
而真机上那是 `<盘根>\.荣盈魔方更新\<事务>\download\portable.zip`，**这棵树此刻还不存在**；
Windows 上 `statfs` 一个不存在的路径抛 ENOENT ⇒ 空间检查先炸。
⚠️ 隔壁 `extractPortablePackage` **早就踩过并修了**（那里注释写着同一个坑、先 `mkdir` 再 `statfs`），
**下载这条路漏了**。单测没抓住是因为夹具的 `destinationPart` 父目录**总是存在的**，而且 `statfsImpl` 是注入的假实现。

**⇒ 结论：「0.0.28 自己升到 0.0.29」不成立** —— 盘上那个版本的下载器本身就是坏的，
而下载动作只能由盘上那个版本执行。现有盘只能**人工换一次基础包**。

## 🔴 修完上面四条之后，真机上又撞上**第二堵墙**：Electron 的 asar fs 补丁

第一堵墙修掉后重跑真机：**下载这次成功了**（406,245,003 B，sha256 与 manifest 逐字相同 ⇒ 完整性门也过），
相位走到 `extracting`，然后失败 —— 这次拿到的是**分类后的** `filesystem-error`（分类修复生效），
盘上日志也第一次留下了一行 `portable.prepare.failed`（日志修复生效）。

**但原始 fs 错误还是没留下**（`mapFileSystemFailure` 把它替换掉了）⇒ 只能再上**主进程调试器**
（`Debugger.setPauseOnExceptions({state:'all'})`）重跑一次，抓到：

```
Error: failed to initialize archive
    at getOrCreateArchive (node:electron/js2c/node_init:…)
    at WriteStream._construct (node:internal/fs/streams:…)
Error: Invalid package E:\.荣盈魔方更新\staged\<事务>\extract\resources\app.asar
```

**根因**：**Electron 把 `fs` 换成了带 asar 支持的版本** —— 路径里只要有 `.asar` 段，就当成
**一个只读的虚拟归档**（官方口径：_"The archives can not be modified so all Node APIs that can
modify files will not work with ASAR archives"_），而我们的包里**就有** `resources/app.asar`
与整棵 `resources/app.asar.unpacked/` ⇒ 解压写到那一步必炸。
⇒ **便携更新永远解压不完**，与 exFAT / 空间 / 网络**全都无关**，每台机器每块盘都一样。
（同类：node-tar #402；Electron 把"访问 asar 文件本身"标为 **wontfix**。）

⭐ **为什么本地怎么测都是好的**：只有 Electron 打过补丁的那个 `fs` 会这样 ——
我用**同一个函数、同一份 zip、同一块盘**写的 Node 探针**解得好好的**（只是慢，8 分 12 秒）。
**这类缺陷只有打包态真机能抓** —— 与 `[[pnpm-flattening-drops-nested-deps]]` 同一形状。

**修法**（`f1ab8004`）：新增 `packages/desktop/src/main/update/asar-safe-fs.ts` ——
解压与校验**全部**走 Electron 的逃生口 `original-fs`（含 `createReadStream`：读 `app.asar` 同样被拦），
纯 Node 里回落 `node:fs`（行为一致）。
⛔ **不用另一个逃生口 `process.noAsar = true`**：那是**全进程**开关，而解压要跑几分钟、
期间应用自己还在读它的 asar ⇒ 全局关掉会把正在跑的读一起打断。

- 测试：4 条新用例钉**选择逻辑**（拿到就用 / 拿不到才回落 / 只拿到半个也回落）；门禁 RC=0
  （desktop **3264** passed；⚠️ 首轮门禁抓到我自己写的 TS 收窄错误 `typeof original` ⇒ `never`，已修）。
- ⚠️ **0.0.30 是修 asar 之前打的包** ⇒ 盘升到 0.0.30 之后**下一次更新还会撞同一堵墙**；
  这个修复必须进**下一个版本**才算真正到用户手上。

## 🔴 第二堵墙修完，真机上撞上**第三堵墙**：两份清单**从来没被写下去**

修完 asar 那条再重跑真机：这次**下载 406,245,003 B 逐字节正确、解压走完、246 个文件逐个校验通过**，
相位走到 `ready` —— 前面三堵墙（空间、网络、asar）都过了。然后点「重启并更新」：
**界面卡在「应用」，盘上的程序目录一个字节都没动。**

**定位过程**（这次的教训：**别信"启动器卡住了"这个表象**）：启动器是被 **detached 拉起**的，
它把失败原因**只写进一个模态对话框**（`MessageBox`）—— 从外面看就是"没反应"。
**手搓一次 `荣盈魔方启动器.exe --apply <状态文件>`**（前台跑、能看到 stdout/对话框）拿到原文：

```
portable launcher: reconciled the disk state: ready
portable launcher: applying the update failed: portable update: manifest is invalid:
open E:\.荣盈魔方更新\staged\5e5e8a0c-aed6-4c08-a5fa-a3d2fff72248\manifest.json:
The system cannot find the file specified.
```

（这条是**真盘上当场取的**：`RC=124` = 我 45 秒 `timeout` 把它杀了 —— 也就是它**确实卡在模态框上**，
"启动器死机"的表象就此解释清楚。同一句也走 `logf` 打到 stdout，所以**下次排障直接前台跑一次就行**。）

**同日、同一块盘上的现场物证**（`ls` 事务目录，逐字）：

```
staged/5e5e8a0c…/        ← 只有这一个子目录
  program/               ← 246 个文件、逐个 sha256 全过（前面全绿）
manifest.json            ← 🔴 不存在
portable-files.json      ← 🔴 不存在
```

**根因**：客户端把 `manifestPath` / `fileManifestPath` **算出来了、也写进事务记录了**，
**却从来没有人把这两个文件放到那两个路径上**。而启动器 `Apply` 的**第一步**就是读它们验签
（`swap.go`：`VerifyStagedTransaction` 先读 `manifestPath`/`fileManifestPath`，再验程序树）
⇒ 每次都在第一步被拒。**便携更新永远卡在「应用」**，与磁盘/网络/权限无关。

⚠️ 为什么单测全绿：夹具里 `verifyTree` 是注入的假实现，**没有任何一条断言问"清单文件存在吗"**；
端到端那条集成测试也只覆盖到打包侧（产出 zip + 清单），**没有"把清单搬进暂存目录"这一步**。

**修法**（`d77f2998`）：服务新增注入点

```ts
writeStagedManifests: (input: {
  paths: { manifestPath: string; fileManifestPath: string };
  manifest: PortableUpdateManifestV1;
  fileManifest: PortableUpdateFileManifestV1;
}) => Promise<void>;
```

真实实现在 `ipc/update-handlers.ts` 里用 **`canonicalizeJson` 逐字节照规范写**（启动器验签用的是
规范化后的字节，写歪一个空格就前功尽弃），先 `mkdir(dirname, {recursive:true})` 再写两份。

⭐ **顺序是这条修复的要点，不是实现细节**：调用点放在
`readyTransaction = await deps.stateStore.write({...})` **之前** —— 事务一旦落成 `ready`，
就代表"**启动器要的东西全都就位了**"；反过来写，崩在中间会留下一份
**`ready` 但缺清单**的事务，那正是真机上把更新永久卡死的那种状态。测试按名钉住这条顺序
（`⭐ 事务写下去**之前**，两份清单已经落到暂存目录（`ready` 才等于"一切都就位"）`，
断言 `seen[0].txFileExists === false`）。

- 读数：新增测试 **+2 条**（顺序 + 准备失败时不写清单）；门禁 **RC=0**（desktop **3266** passed / 2 skipped、
  core 673、pwa 61、shared 124）；**变异电池 3 杀 + 1 对照，RC=0**（收集 30/30、锚点唯一、还原逐字）。
  ⚠️ 电池里 M1（把调用挪到事务之后）**首轮存活** —— 因为 `setTimeout(…, 0)` 的写入与同步的
  `stateStore.write` 抢时序；补一条"两步"变异（先删原调用、再插到 `write` 之后）才杀掉。
  **记下来：靠时序取胜的守护测试，必须用"挪位置"而不是"加延迟"来验。**

### 三堵墙合起来说明的一件事

三条**全都是同一种缺陷**：**装到真盘上才存在的路径**（不存在的目录 / `.asar` 段 / 启动器读的那两个文件）
**在单测的注入夹具里全都被绕过去了**。三条里前两条靠真机日志 + 主进程调试器抓到，
第三条靠**手动前台跑一次启动器**拿到原文。
⇒ 便携更新这条链的测试缺口是**结构性的**：夹具把"盘上真实形状"抽象掉了。
真正该补的是**一条对着真实文件系统的集成测试**（真目录、真 asar 段路径、真读清单），
而不是再往注入点上堆假实现。**这一条留作下一步（见阶段 7）。**

## 🔴 第四堵墙：启动器换目录时**抢不过应用自己的退出**（真机上第一次点「重启并更新」必失败）

**症状**：在应用里点「重启并更新」⇒ 启动器起了、进度屏「正在更新，请勿拔出 U 盘。」、
`backup/` 目录建出来了（说明验签+验树全过），然后 —— **卡住**。
盘中程序目录一个字节没动，事务停在 `ready`。

**原文**（前台手搓同一条命令拿到；启动器被应用拉起时 `stdio:'ignore'`，stderr 全丢）：

```
portable launcher: reconciled the disk state: ready
portable launcher: applying the update failed:
rename E:\荣盈魔方 E:\.荣盈魔方更新\backup\<事务>: Access is denied.
```

**机理（实测，不是推断）**：程序目录**只要有进程占着就不能改名**。

- 应用**正在跑**时做同一次 `MoveFileExW` ⇒ **Win32 错误码 32（Sharing violation）**；
- 什么都没有时 ⇒ **成功**；
- 而启动器**一次都不重试**，失败即弹模态框、放弃。

⇒ **这是一个竞态**：应用 `startLauncher()` 在 `spawn` 事件上就 resolve，**紧接着** `app.quit()`；
启动器只需几秒就验完 246 个文件，而 Electron 退出要杀网关运行时、落盘状态 ⇒
**启动器几乎总是先到那一步，而应用还没退干净** ⇒ 第一次点必然失败。

⚠️ **而且它不自愈**：`main.go` 的 `if parsed.mode == modeApply && transaction.Phase == "ready"`
—— 只有 `--apply`（点「重启并更新」）才会应用；**正常双击启动器走 `launchProgram`，看到 `ready` 也不管**。
用户重新开一次盘，更新纹丝不动，只能再点一次「重启并更新」⇒ **再输一次同一场竞态**。
**这正是现象层「为什么一直失败」的答案。**

**修法（未做，需拍）**：`Apply` 里换目录之前**带上限重试**（锁类错误 5/32/33，间隔 ~500 ms、上限 ~60–120 s），
进度屏本来就在说"请勿拔出"，等一会儿是诚实的。
`Ops` 接口里**已经有 `Sleep`**（`WaitForHealth` 在用）⇒ 用现成的假 `Ops`（失败 N 次后成功）就能 TDD。

⛔ **但这条修复到不了任何一块现有盘**：便携更新**从不替换启动器**（那是信任根）。
⇒ 启动器侧的任何缺陷**只能靠换新基础包**（或者另建启动器自更新通道 —— 现在没有）。
**这条才是本次验收最重要的一条结论**：便携更新的修复能力**止于客户端**。

### ⭐⭐ 第五刀：重试**单独不够用** —— 这类拒绝是"关于调用者"的，等多久都没用

量出来的（一条真 Windows 测试，0.5 秒跑完，现在可回归）：

```
1. 本进程的工作目录 = 目标目录  ⇒ 改名真的被拒：Win32 32（sharing violation）
2. 等 500 ms 再来一次           ⇒ 还是被拒（拒的是"调用者自己"，不是时机）
3. 先 os.Chdir 出去再改名       ⇒ ✅ 成功
```

⇒ **启动器是被应用拉起的、继承应用的 CWD，而应用通常正是从程序目录启动的** ——
那种情况下 `renameWithRetry` 只会白烧 90 秒再失败。所以 `run()` 一进来就
`os.Chdir(filepath.Dir(deps.launcherPath))`（离开到盘根；下面所有路径本来就是绝对的，不花代价）。

**顺带杀掉的两个"想当然"**（都写下来，别再猜）：

- ❌ **"进程把目录当工作目录就会挡住改名"** —— 那只对**改名者自己**成立；别的进程待在里面**不挡**。
- ❌ **"目录里跑着可执行文件（镜像被映射）会挡住改名"** —— 实测**不挡**。
- ⚠️ **`testing.T.Chdir` 自己会留一个指向旧目录的句柄**（为了测试结束还原）—— 那个句柄**恰好就是挡路的东西**，
  于是"离开之后仍被拒"看起来像 Windows 的行为，其实是**测试工具**造成的。本轮在这上面栽了一次，
  最后改成裸 `os.Chdir` + `defer` 还原。

**测试套件的两处加固**（被第五刀逼出来的，都是真缺陷）：

## 🟡 顺手查出的一条（不阻断、未修）：**一次成功更新在盘上永久留下 ~1.2 GB**

换目录成功后**没有任何东西清理**更新目录。真盘实测：


⇒ U 盘每升一次少 ~1.2 GB，且**没有任何界面告诉用户这些能删**。
**建议**（未做，与第四堵墙同批考虑）：`committed` 之后删 `download/<事务>` 与 `backup/<事务>`（旧的留最近一次当人工回滚材料），
