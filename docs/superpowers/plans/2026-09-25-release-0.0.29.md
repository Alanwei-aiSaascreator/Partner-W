## 🔴 真机验收抓到的更新链缺陷（0.0.28 与 0.0.29 这段代码**逐字相同**，两个版本都有）

**症状**：点下载 ⇒ `{ok:false, error:'unknown'}`、相位 `error`，**连 `portable.zip` 都不去取**。

**定位过程**（记下来，下次别重走）：盘上日志里 `updater` 域**一条都没有** ⇒ 只能挂
**主进程 Node inspector**（`--inspect`）才捞得出来：`Debugger.setPauseOnExceptions({state:'all'})`
抓到

```
Error: ENOENT: no such file or directory, statfs
       'E:\.荣盈魔方更新\download\<事务 id>'
```

**根因**：`downloadPortablePackage` 直接用 `fs.statfs` 量 `dirname(destinationPart)` ——
而真机上那是 `<盘根>\.荣盈魔方更新\<事务>\download\portable.zip`，**这棵树此刻还不存在**；
Windows 上 `statfs` 一个不存在的路径抛 ENOENT ⇒ 空间检查先炸。
⚠️ 隔壁 `extractPortablePackage` **早就踩过并修了**（那里注释写着同一个坑、先 `mkdir` 再 `statfs`），
**下载这条路漏了**。单测没抓住是因为夹具的 `destinationPart` 父目录**总是存在的**，而且 `statfsImpl` 是注入的假实现。

**⇒ 结论：「0.0.28 自己升到 0.0.29」不成立** —— 盘上那个版本的下载器本身就是坏的，
而下载动作只能由盘上那个版本执行。现有盘只能**人工换一次基础包**。

### 一并修掉的四条（`packages/desktop/src/main/update/`）

| #    | 缺陷                                                                                               | 修法                                                                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 🔴 | 下载前 `statfs` 一个还没建的目录 ⇒ ENOENT ⇒ 更新**永远失败**                                       | `portable-package.ts`：下载前先 `mkdir(dirname(destinationPart), {recursive:true})`（与解压那条对齐）                                              |
| 2    | `statfs` 自己失败是**裸抛**（普通 `Error`）⇒ 服务只能报 `unknown`                                  | `assertFreeBytes` 把 `statfsImpl` 的异常经 `mapFileSystemFailure` 归类（`disk-space`/`volume-readonly`/`filesystem-error`）                        |
| 3    | `fetch` 连不上（undici 的 `TypeError: fetch failed`）与非 2xx 的 `new Error(...)` 都落进 `unknown` | 新增 `fetchFeedResponse`（⇒ `network`，词表里本来就有，**可重试**）与 `readFeedJson`（⇒ `feed-response`）；`update-handlers.ts` 两处取清单都改用它 |
| 4    | 这条路**一条日志都不写** ⇒ 现场无法诊断                                                            | `portable-update-service.ts` 的 `check` / `prepare` 两个 catch 各写一条 `updater` 域 warn（带归类后的 code 与原始 message）                        |

- 读数：新增/改动测试 **+7 条**（包 5、服务 2）；`portable-update-*` 九个套件 **175 条全绿**；
  **变异电池 7 条 = 6 杀 + 1 对照，RC=0**（收集 77/77、锚点唯一、还原逐字）。
  ⚠️ 电池自己抓到一次锚点不唯一（`'network'` 在文件里有两处）⇒ 收紧到带 `catch` 的那一处。
- 📌 一条**更正**：我先前报的"失败后不再重试、必须重启"是**探针只记失败、不记成功**造成的误判；
  服务里本来就有"网络失败后下一次 check 能成功"的用例（`portable-update-service.test.ts`）。**这条不成立**。
