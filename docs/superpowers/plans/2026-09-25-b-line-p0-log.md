## P0-2（B 侧）：让界面说得出"为什么起不来"

### 四刀

| 提交       | 内容                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------- |
| `682de211` | `GatewayFailureReason` 闭集（5 个值）+ `gatewayFailureReasonFrom`（白名单，不是黑名单）     |
| `af52cd70` | 主进程 → 渲染层的贯通：窄签名映射、快照 + 初始读、store 切片、推导层暴露 `ai.failureReason` |
| `b64290af` | ⭐ **删掉一个仓库里没人产生的错误码**（见下）                                               |
| `b05cdd19` | WS 终端路径：网关明确拒绝（1008）时带上"哪一类拒绝"                                         |

### 闭集（界面上要说的每一句话都对应这里的一个值）

`port-occupied` / `auth-rejected` / `process-exited` / `ready-timeout` / `unknown`

- **白名单**：不认识的中转码落 `unknown`，不许"找最接近的那一类"。
- **原始文本一个字节都进不来**：映射函数的入参收窄成 `{ ok, code }`，拿不到人看的那条
  `reason`（带路径/端口）⇒ **结构上**带不出去。测试拿一个含 token、手机号、路径的字符串
  喂进去，断言它出不来。
- 判定优先级：中转码 > 关闭码。两处都有值时**"我们自己的网关没起来"赢**（被拒说明网关是起来的）。

### ⭐ 本轮最该记住的事实：`AUTH_TOKEN_MISMATCH` 不存在

用户指令里把它当成认证拒绝的信号。**查下来整个仓库没有任何地方产生它** ——
客户端没有、网关入口没有、测试夹具也没有。我第一版照着认了它，`b64290af` 删掉了。

真实形状只有一条：网关回 `res.error` ⇒ `isGatewayRejection` 判真 ⇒ 客户端主动
`ws.close(1008, 'auth failed')` ⇒ close 处理器报 `gaveUp: true`。
所以 **1008 是唯一可靠信号**，它现在也是通往 `auth-rejected` 的唯一一条路。

教训：认一个不存在的码看着无害，其实是**把猜测写进了判据** —— 猜错的时候是**无声**的。

### 两个维度**刻意不合并**

| 字段                      | 说的是什么                         | 什么时候有值                       |
| ------------------------- | ---------------------------------- | ---------------------------------- |
| `runtimeBootstrapFailure` | 我们**自己**那个网关进程有没有起来 | 端口被占 / 等就绪超时 / 子进程早退 |
| `gatewayReconnect.reason` | 连上了没有、被拒了没有             | 网关明确拒绝（1008）               |

合并的后果是界面自相矛盾（"连上了"却显示"端口被占"）。它们可以同时成立。

### 两条"反向假话"的守卫

- **连上了 ⇒ 清掉失败原因**：用户可能自己把网关起起来了，或这一份连的是别的网关 ——
  那时候继续挂"18789 被占用"就是**反向的假话**。清理判据是"**当前**连上了"，不是"曾经失败过"。
- **没给原因 ⇒ 存的那份也没有原因**：不替它编一个 `unknown` —— 那会把"还在重连"说成"出错了"。

### 与"清理"有关的一条反直觉决定

`runtimeBootstrapFailure` **刻意不跟着账号走**（退出/切号**不清**）：端口被占是**这台机器**
此刻的事实，换个账号登录，18789 照样被占着。清掉就是把一条真实结论抹成"没结论"。
（旁边的 `gatewayReconnectInfo` 要清，因为那是连接状态，切号会重建连接。）

### 竞态：这条结论往往在窗口之前就产生了

bootstrap 在 `app.whenReady()` 里就跑，窗口与渲染层是**之后**才挂上来的 ⇒ 推送没人收
（窗口不在时 `sendToWindow` 返回 false）。所以有**快照 + 初始读**（`runtime:bootstrap-status`），
形状照抄 relay 公开状态（`main/ipc/commercial-handlers.ts` 有同一段理由）。补读失败留一条遥测。

### 变异电池抓出来的、值得留档的三件

1. **一条测不出东西的测试**：`.catch` 是空操作时，`expect(() => …).not.toThrow()` 证明不了
   catch 在不在（抛是异步的）。改成让 catch 留一条遥测，判据落在遥测上。
2. **我写错了两个变异**：一个"改坏了但实际抛异常"（所以测试照样绿），一个"根本没真的取消订阅"。
   变异写错和实现写错**长得一样**，都得当场查清楚是哪一个。
3. **一条我以为该红的测试没红** —— 查下来是**两个测试独立**（各有各的判据），不是冗余。
   这条差别值得每次都想一遍。

## 残留风险

- **真机未验**：端口被占 / 认证拒绝 / 等就绪超时这三条真路径，一次都没在真机上走过。
  验收口径应包含"拔掉一个占用 18789 的程序再看界面说什么"。
- **`unknown` 的占比未知**：真实世界里落 `unknown` 的比例是多少，要等真机日志（
  `renderer.runtime_status.read_failed` 那条遥测就是为这个留的）。
- **`gatewayReconnect.reason` 只在 1008 路径有生产者**：别的拒绝形状（如果网关将来换了）会落
  `unknown` —— 这是**故意**的（不猜），但要在真机上核一遍不会因此说出错话。
